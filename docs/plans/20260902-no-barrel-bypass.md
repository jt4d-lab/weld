# Правило `weld/no-barrel-bypass`

## Overview

Первое правило плагина. Директория, в которой появился файл `index.*`, объявляет себя модулем с
публичным API. Правило ловит импорты, входящие внутрь такой директории мимо её точки входа, и
сообщает корректный путь.

Правило проектно-нейтральное: оно ничего не знает ни про слои, ни про имена директорий. Единственный
источник знания о границах — расположение файлов `index` на диске.

Решает главную проблему подхода WELD: договорённостями границы модулей не удерживаются. Заодно
включает два инварианта в `tests/plugin.test.ts`, которые сейчас крутятся вхолостую по пустому
реестру.

## Solution Overview

Ядро — три чистые функции, один предикат в порту, ноль обращений к диску за целью импорта.

Строка импорта сама и есть путь: относительная резолвится от директории файла, алиасная —
подстановкой якоря. Последний сегмент пути цели считается не-директорией и в обходе не участвует.
Диск трогает единственный предикат `hasEntryPoint(dir)`, инжектируемый через порт.

```
specifier ──parseSpecifier──▶ Target {path, form}
                                 │
                    findBarrier(fromDir, path, hasEntryPoint) ──▶ D | null
                                 │
                    renderSpecifier(form, fromDir, D, aliases) ──▶ исправленный путь
```

Ключевые решения и их причины:

- **Резолвер не нужен.** Проверка существования цели — дело `import/no-unresolved`. Отказ от
  резолвера сохраняет нулевые runtime-зависимости и делает ядро строковым.
- **Пути в ядре — абсолютные posix-строки** (тип просто `string`, без брендов). Абсолютные потому,
  что вся арифметика построена на общем префиксе сегментов, а он осмыслен только когда `..`
  схлопнуты. Импорты в соседние пакеты монорепы штатны, и при путях от корня они дают ведущие `..`,
  после которых обход уходит в бессмыслицу молча.
- **`node:path/posix` в ядре не используется.** На Windows нормализованный `C:/p/src` для posix не
  абсолютен, и `relative()` молча дорезолвит его от `process.cwd()` — скрытая зависимость от
  глобального состояния прямо в ядре. Вместо него свои сегментные функции.
- **Форма вывода берётся из формы исходного импорта, а не из пути цели.** Абсолютный путь про форму
  записи ничего не знает; `renderSpecifier` получает разобранную `form`, поэтому строка импорта
  разбирается ровно один раз.
- **Верхняя граница выигрывает у ближней.** Вложенные `index` — деталь устройства модуля, снаружи
  они не видны.

## Technical Details

### Типы

```ts
type Alias = { prefix: string; anchor: string };
type Form = { kind: 'relative' } | { kind: 'alias'; alias: Alias };
type Target = { path: string; form: Form };
type CheckInput = { specifier: string; fromFile: string; aliases: Alias[] };
type CheckEnv = { hasEntryPoint(dir: string): boolean };

parseSpecifier(specifier: string, fromDir: string, aliases: Alias[]): Target | null;
findBarrier(fromDir: string, targetPath: string, hasEntryPoint: (dir: string) => boolean): string | null;
renderSpecifier(form: Form, fromDir: string, barrier: string, aliases: Alias[]): string;
checkImport(input: CheckInput, env: CheckEnv): string | null;
```

`checkImport` = `parseSpecifier` → `findBarrier` → `renderSpecifier`; возвращает исправленный путь
или `null`. Найденная граница наружу не отдаётся: в сообщение она не попадает, а сама по себе
проверяется тестами `findBarrier`.

`CheckEnv` объявляется в `check.ts`, рядом с потребителем; `src/env/entry-point.ts` импортирует этот
тип. Стрелка «реализация порта зависит от контракта, а контракт принадлежит потребителю» — то, что
нужно, отдельный файл под однострочный тип — нет.

### Алгоритм `findBarrier`

Обозначения: `F` — файл с импортом, `T` — путь цели, `M` — самая глубокая общая директория
`dirname(F)` и `dirname(T)`, `D` — найденная граница.

1. `M` = общий префикс сегментов `dirname(F)` и `dirname(T)`. Общего корня нет (разные диски) →
   нарушения нет.
2. Сегменты `relative(M, T)`; последний сегмент — имя файла, в обходе не участвует.
3. Идти по сегментам-директориям сверху вниз, накапливая `D`, на каждой проверять точку входа.
4. На первой `D` с точкой входа: если `T` это `D/index` или `D/index.<ext>` — нарушения нет, иначе
   нарушение с границей `D`.
5. Сегменты кончились — нарушения нет.

Границы, внутри которых уже находится `F` (то есть на уровне `M` и выше), не проверяются: модуль не
закрыт от самого себя. Ниже `M` положение `F` роли не играет — важно лишь, какие границы импорт
пробивает, спускаясь к `T`.

Отдельной проверки `F === T` нет: она избыточна. При совпадении `dirname(F)` и `dirname(T)` равны
`M`, после отбрасывания последнего сегмента директорий для обхода не остаётся, и шаг 5 даёт `null`.

Таблица свойств (каждая строка — отдельный тест):

| ситуация                                              | результат                       |
| ----------------------------------------------------- | ------------------------------- |
| `F` и `T` в одной директории                          | разрешено                       |
| `T` выше `F` по дереву                                | разрешено                       |
| `T` внутри соседней директории с `index`              | нарушение, `D` = эта директория |
| `T` — сам `index` первой границы на пути              | разрешено                       |
| `T` — `index.<ext>` первой границы (явное расширение) | разрешено                       |
| `T` — `index` директории глубже первой границы        | нарушение, `D` = первая граница |
| на пути нет ни одной точки входа                      | разрешено                       |
| у `dirname(F)` и `dirname(T)` разные корни            | разрешено                       |

### Точки входа

Расширения: `ts`, `tsx`, `js`, `jsx`, `mts`, `cts`, `mjs`, `cjs`. Общая константа `ENTRY_EXTENSIONS`
в `src/entry-extensions.ts` — нужна и нормализации якорей, и `findBarrier`, и fs-реализации порта.

### Что отсекается на входе

`parseSpecifier` возвращает `null`, не доводя до арифметики:

- голое имя пакета и `@scope/pkg` — `node_modules` не резолвится вовсе;
- абсолютный специфаер (`/foo`) — форма вывода для него не определена;
- специфаер с `?` или `!` (`./x.svg?url`, `!!raw-loader!./x`) — это не путь, а инструкция сборщику;
- последний сегмент с расширением вне `ENTRY_EXTENSIONS` (`.css`, `.svg`, `.json`, `.png`).

Последний пункт — сознательное сужение. Формально импорт `./feature/internal/styles.css` пробивает
границу так же, как импорт кода, но баррель `index.ts` реэкспортировать CSS не может: предложенная
правка была бы невыполнимой, а с `fix: true` — ломающей сборку. Правило молчит там, где не может
предложить работающий путь.

### Формирование исправленного пути

Форма записи исходного импорта сохраняется:

1. относительный импорт → `relativePath(dirname(F), D)`, с префиксом `./` если результат не
   начинается с `./` или `../` (директории вида `.storybook` дают путь, начинающийся с точки, но
   относительным специфаером от этого не становятся);
2. алиас, чей якорь покрывает `D` → тот же алиас;
3. якорь исходного алиаса не покрывает `D` → алиас с самым длинным якорем среди покрывающих `D`;
4. ни один алиас не покрывает `D` → откат на относительный путь.

`D` — всегда директория, поэтому ни расширение, ни хвост `/index` в результат не попадают. При
`D === anchor` результат — голый префикс, без завершающего слэша.

### Алиасы

Источник — `settings.weld`, формат совпадает с `paths` из `tsconfig`:

```js
settings: {
    weld: {
        baseUrl: 'packages/app',          // необязательно, по умолчанию '.'
        aliases: { '@src/*': ['src/*'] },
    },
}
```

`<base>` = `resolvePath(cwd, baseUrl ?? '.')`, где `cwd` — `context.cwd`. Отличие от tsconfig: там
база отсчитывается от расположения конфига, здесь — от текущей директории ESLint, поэтому в монорепе
результат зависит от того, откуда запущен линт. Это должно быть написано в документации правила.

Нормализация — обе стороны записи обрабатываются независимо, звёздочность ключа и якоря совпадать не
обязана:

| запись                                  | префикс | якорь                     | почему                                                        |
| --------------------------------------- | ------- | ------------------------- | ------------------------------------------------------------- |
| `'@src/*': ['src/*']`                   | `@src`  | `<base>/src`              | снят хвост `/*` с обеих сторон                                |
| `'@pkg': ['packages/pkg/src/index.ts']` | `@pkg`  | `<base>/packages/pkg/src` | базовое имя `index` + известное расширение → берём директорию |
| `'@cfg': ['src/config.ts']`             | `@cfg`  | —                         | обычный файл директорией не выражается, запись отбрасывается  |
| `'@dir': ['src/dir']`                   | `@dir`  | `<base>/src/dir`          | как есть                                                      |

Префикс всегда без завершающего слэша. Специфаер подходит под запись, если он равен префиксу или
начинается с `prefix + '/'` — **включая беззвёздочные записи**. Это отход от tsconfig, где `'@pkg'`
без `*` означает точное совпадение: `@pkg/internal/thing` — ровно тот обход границы, который правило
и должно ловить, поэтому такие записи трактуются как префиксные.

Прочие решения по алиасам:

- массив якорей разворачивается в отдельные записи `{ prefix, anchor }`, дубликаты `prefix + anchor`
  схлопываются;
- при разборе строки импорта выигрывает **самый длинный подходящий префикс**; при равных префиксах —
  первая запись в порядке объявления (порядок массива якорей и есть порядок приоритета в tsconfig);
- при рендере — запись с самым длинным якорем, покрывающим `D`;
- принимаются только ключи и якоря либо без `*`, либо оканчивающиеся на `/*`. Формы со звёздочкой в
  середине (`'@a/*/b'`, `'src/*.ts'`) отбрасываются: подстановкой префикса они не выражаются;
- запись `'*': [...]` отбрасывается принудительно: пустой префикс совпадёт с чем угодно, и `lodash`
  поедет в арифметику путей как относительный к якорю — отсев пакетов сломается молча;
- валидация: `aliases` не объект, значение не строка и не массив, элемент не строка → исключение с
  текстом, называющим конкретный ключ. Значение-строку вместо массива принимаем: в tsconfig так
  нельзя, но это частая опечатка от руки с однозначным смыслом; отход от формата-источника надо
  упомянуть в документации. Отброшенные по таблице записи молчат — это валидный `paths`, просто
  невыразимый директорией;
- разбор кэшируется в `WeakMap` по объекту `settings.weld`: во flat config у разных файлов могут
  быть разные `settings`, поэтому ключ — объект, а не глобальный singleton. Нет `settings.weld` →
  сразу `[]`, минуя кэш.

### Правило

```ts
create(context) {
    const aliases = readAliases(context.settings, context.cwd);
    const fromFile = toPosix(context.filename);
    const { fix = false } = context.options[0] ?? {};
    …
}
```

- узлы: `ImportDeclaration` (включая `import type`), `ImportExpression` со строковым литералом,
  `CallExpression` вида `require('…')`. `require` распознаётся синтаксически, затенение локальной
  переменной не отслеживается. Сообщение вешается на литерал пути;
- `export … from` не проверяется вовсе — сознательное решение, см. Out of scope;
- `meta.type` — `'problem'`: нарушен архитектурный контракт, а не стиль;
- `meta.messages` — два: `bypass` =
  `Import bypasses the module barrel. Use '{{suggestion}}' instead of '{{original}}'.` и `useBarrel`
  = `Import through '{{suggestion}}'.` для suggestion. Сообщения на английском, как у остальных
  правил ESLint;
- `meta` всегда объявляет `fixable: 'code'` и `hasSuggestions: true`; опция `fix` (по умолчанию
  `false`) решает только, куда уходит одна и та же функция правки — в `fix` или в `suggest`. Причина
  выключенного автофикса: правило не читает баррель и не знает, реэкспортирует ли тот нужное имя,
  поэтому `--fix` способен подставить корректный путь и сломать сборку;
- кавычки при замене берутся из `source.raw[0]`, иначе автофикс переведёт проект на свой стиль
  кавычек и подерётся с prettier;
- `schema` — один объект `{ fix: boolean }` с `additionalProperties: false`;
- если `context.filename` не абсолютный (`<input>` при `lintText` без пути) — выходим сразу,
  арифметике не от чего отсчитывать;
- исключение из `readAliases` бросается внутри `create()`, то есть при неверных `settings` ESLint
  сообщит об ошибке правила на каждом проверяемом файле. Это громко и намеренно: молча отключившееся
  правило хуже упавшего. Поведение должно быть описано в документации;
- правило входит в `configs.recommended` как `'error'`.

### Кэш точек входа

`Map` внутри замыкания `createEntryPointEnv` с TTL 30 секунд (значение по умолчанию у
`import/cache`). Замыкание, а не модульная переменная: срок жизни тот же — `createEntryPointEnv()`
вызывается один раз при загрузке модуля, — но каждый тест получает свой чистый кэш и не делит
состояние с интеграционными тестами.

Кэш нужен: границы проверяются заново для каждого файла, а без инвалидации ломается IDE, где
ESLint-сервер живёт часами и не увидит только что созданный `index.ts`. Часы и `existsSync`
инжектируются параметрами, чтобы TTL тестировался без ожидания.

## Out of scope

Сознательно не входит в задачу:

- проверка `export … from` и правило «баррель реэкспортирует только на один уровень»;
- чтение содержимого барреля и разворачивание цепочек реэкспорта;
- дополнительные точки входа (соглашения вида `rsc.ts`) — гасятся через `files`/`ignores` во
  flat-конфиге;
- SFC-баррели (`index.vue`, `index.svelte`): `ENTRY_EXTENSIONS` фиксирован восемью JS/TS
  расширениями;
- импорты не-JS ресурсов и специфаеры с `?`/`!` — см. «Что отсекается на входе»;
- выбор между относительным путём и алиасом — это будущее правило `no-relative-root-path`, которого
  в репозитории нет;
- документация подхода WELD целиком — в этой итерации пишется только страница правила;
- расширение `scripts/smoke-test.sh` до проверки самого правила: smoke остаётся проверкой упаковки и
  подключения, срабатывание правила из тарбола не проверяется.
