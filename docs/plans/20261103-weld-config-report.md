# Полный диагностический вывод `weld config`

## Цель

Расширить `weld config <path>`, чтобы команда показывала все доступные эффективные настройки WELD,
включая разобранную схему слоев, и помогала исправлять ошибки конфигурации. Независимые настройки
должны отображаться даже при ошибке другой настройки, но результат не должен содержать значений,
полученных спекулятивно через неразрешенную зависимость.

Правила ESLint и `weld inspect` сохраняют текущее бросающее поведение. Для правила достаточно
получить исключение, как сейчас; диагностический частичный отчет нужен только команде `config`.

## Контекст

- `src/cli/config.ts` собирает эффективные настройки через `resolveForFile`.
- `src/config/resolve.ts` предоставляет ленивый `WeldTarget`: корень, алиасы и схему вычисляются
  только при обращении.
- `src/settings/weld.ts` применяет значения по умолчанию, приоритеты `options` над `settings.weld` и
  кэширует успешный разбор.
- `src/settings/layers.ts` сейчас разбирает схему целиком и бросает на первой ошибке.
- `src/cli/render.ts` печатает текст и JSON, а `src/cli/program.ts` уже устанавливает код возврата 1
  для ошибки действия.
- Автоматический поиск `tsconfig` намеренно возвращает `null` и пишет debug при проблемах; изменение
  этого контракта в задачу не входит.
- Форматирование выполняется pre-commit hook; `prettier`, `eslint --fix` и аналогичные команды
  вручную не запускать.

## Решение

### Состояния настроек

Отчет различает четыре состояния значения:

- значение — настройка успешно разобрана;
- `invalid` — собственное значение настройки невалидно, в отчете сохраняется текст ошибки;
- `unresolved` — значение нельзя вычислить из-за неразрешенной зависимости; новая собственная ошибка
  для него не создается, зависимость указывается в отчете;
- `not set` — допустимое отсутствие необязательного значения, прежде всего `layers` или
  `moduleLayers` без схемы слоев.

Код 1 возвращается, если есть хотя бы одна собственная ошибка настройки. `unresolved` и `not set`
сами по себе код возврата не меняют.

Собственное значение `repoRoot` и имя `tsconfig` проверяются независимо до вычисления эффективного
корня. Это позволяет показать обе ошибки, даже если `getRoot()` сначала наткнулся бы на невалидный
`tsconfig`. Если `repoRoot` валиден, но эффективный корень нельзя получить из-за `tsconfig`, он
получает `unresolved: tsconfig`. Порядок вычисления в правилах и `inspect` не меняется.

Когда эффективный корень не получен, `file` и `config` печатаются абсолютными исходными путями;
схема и независимые настройки все равно запрашиваются. Явные алиасы разбираются без рабочего корня;
автоматически найденные алиасы получают `unresolved`, если им не хватает корня или имени tsconfig.

Невалидная секция `settings.weld` дает одну собственную проблему с именем `settings.weld`.
Настройки, которые нельзя прочитать из секции, получают `unresolved: settings.weld`; собственные
значения из опций правила проверяются независимо. Вычисление эффективных значений по-прежнему
учитывает их зависимости. Слой `settings` предоставляет для этого необходимый диагностический
интерфейс, не раскрывая формат секции другим слоям.

При невалидном `aliasesBaseUrl` собственная ошибка формата явных `aliases` все равно показывается.
Если собственный формат алиасов корректен, но для их разбора не хватает базы, результат —
`unresolved: aliasesBaseUrl`; фиктивная база не подставляется. Собственная проверка учитывает те же
отбрасываемые записи, что текущий разбор; бросающий разбор сохраняет прежний порядок ошибок.

Файл вне вычисленного корня остается отказом команды, а не состоянием диагностического отчета:
сопоставить цель с конфигурацией невозможно, поэтому сохраняется существующая ошибка
`<path> is outside the repository root`.

### Разбор схемы

Добавить небросающий разбор полей схемы, не меняя контракт существующего `parseScheme` для правил и
`inspect`.

- `srcDir` и `modulesDir` с дефолтами разбираются независимо от списков слоев.
- Отсутствующие `layers` и `moduleLayers` представлены как `not set` и не являются ошибкой команды.
- Сначала проверяются собственный формат и элементы каждого списка, затем — зависимости от
  `modulesDir` и совместимость списков. Невалидное поле получает собственное сообщение с исходником
  и индексом, даже если его зависимость не разрешена. Корректное поле, которое нельзя полностью
  проверить из-за зависимости, получает `unresolved`.
- Совместные проверки списков выполняются, только когда оба списка доступны; отсутствие одного не
  превращает другой в ошибку. Ошибка общего имени или отсутствующего `@modules` прикрепляется к
  соответствующему полю.
- Бросающий `parseScheme` использует тот же разбор и выбрасывает первую ошибку в прежнем порядке,
  включая порядок элементов списка. `getScheme()` сохраняет порядок чтения источников, ленивость,
  кэширование успешного результата и повторную выдачу ошибок.

### Отчет и CLI

В `src/config/` добавить отдельную функцию отчета над тем же `resolveForFile`, например
`reportForFile(input, fsHostOverride?)`. Она собирает состояния по графу зависимостей и не меняет
`WeldTarget` или адаптер `src/rules/context.ts`.

Отчет содержит состояния эффективного `repoRoot`, `aliasesBaseUrl`, `tsconfig`, разобранных
`aliases`, `srcDir`, `modulesDir`, `layers`, `moduleLayers`, а также собственную проблему секции
`settings.weld`, если она есть. Имена настроек и английские сообщения позволяют построить вывод и
определить код возврата.

Путь ESLint-конфига и `sampleOf` остаются в CLI: их нет во входе `resolveForFile`. CLI формирует
`file` и `configFile` по эффективному корню либо использует абсолютные пути, когда корень не
получен; файл вне вычисленного корня остается отдельной ошибкой команды.

Слой CLI преобразует модель отчета в текстовую и JSON-формы:

- текст сохраняет текущие `file`, `config`, `settings.weld`, добавляет четыре поля схемы;
- `invalid` печатается на месте настройки с сообщением ошибки; ошибка самой секции печатается один
  раз;
- `unresolved` печатается как `(unresolved: <dependency>)`;
- `not set` печатается как `(not set)`;
- списки схемы печатаются разобранными значениями в исходном порядке;
- JSON сохраняет простые значения, а недоступные значения представляет как `null`;
- JSON добавляет объект `problems`, ключ которого — имя настройки или секции: для `invalid` значение
  содержит `status` и `message`, для `unresolved` — `status` и `dependency`; `not set` представлено
  значением `null` без записи в `problems`;
- при наличии хотя бы одного `invalid` `program.ts` печатает отчет и устанавливает код 1 без
  выбрасывания исключения; сам по себе непустой `problems` кода 1 не означает;
- сообщения об ошибках в отчете очищаются от управляющих символов так же, как обычные ошибки CLI;
- цветной и `--no-color` вывод используют те же правила, что остальные строки CLI.

Пример JSON для невалидного корня, зависимых от него алиасов и отсутствующего списка слоев:

```json
{
    "settings": {
        "repoRoot": null,
        "aliases": null,
        "layers": null
    },
    "problems": {
        "repoRoot": {
            "status": "invalid",
            "message": "settings.weld.repoRoot must be a string, got number"
        },
        "aliases": {
            "status": "unresolved",
            "dependency": "repoRoot"
        }
    }
}
```

В примере показаны только относящиеся к состояниям поля; полный отчет сохраняет остальные поля.

Диагностика ошибок содержимого автоматически найденного `tsconfig` не добавляется: слой
`src/tsconfig/` продолжает возвращать `null`, а отсутствие найденных алиасов остается пустым
результатом.

## Критерии приемки

- Валидный `weld config` показывает все текущие настройки, алиасы и разобранную схему.
- Отсутствие `layers`/`moduleLayers` не ломает `weld config` и не дает код 1.
- Ошибки `repoRoot` и `tsconfig` видны независимо; неразрешенный корень не приводит к ложным
  относительным путям или автоматически найденным алиасам.
- Ошибка одной настройки или секции не превращается в несколько одинаковых собственных проблем из-за
  зависимых полей; собственные ошибки зависимых полей не скрываются.
- JSON различает `invalid`, `unresolved` и `not set` через значения и объект `problems`.
- Сообщения частичного отчета очищаются от управляющих символов так же, как обычные ошибки CLI.
- Правила ESLint и `weld inspect` по-прежнему получают исключение при запросе кривой схемы.
- `yarn verify` и `yarn smoke` проходят.
