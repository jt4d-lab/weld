# Слои задаёт проект

Состав слоёв — это часть архитектуры конкретного проекта. Универсального списка слоёв, подходящего
для любого проекта, не существует.

Каждый проект самостоятельно определяет, какие слои ему нужны, где проходят их границы и какую
ответственность несёт каждый из них.

Поэтому одинаковые по назначению части системы могут находиться в разных слоях в разных проектах.
То, что в одном проекте выделено в отдельный слой, в другом может быть частью существующего слоя.

## Какую проблему решает

Попытка использовать заранее заданный набор слоёв заставляет проект подстраиваться под чужую
архитектуру вместо того, чтобы отражать собственные требования.

Это приводит к искусственным границам: появляются слои без самостоятельной ответственности,
функциональность приходится перемещать между ними только ради соответствия шаблону, а исключения
начинают восприниматься как ошибки.

Слои должны описывать структуру конкретного проекта, а не соответствие универсальной классификации.

## Правила

1. **Состав слоёв определяет проект**

    Проект сам определяет список слоёв, их количество и границы. Названия и состав слоёв из других
    архитектур не являются обязательными.

    Новый слой следует вводить тогда, когда он выражает самостоятельную архитектурную границу, а не
    только потому, что такая граница существует в другом проекте.

2. **Допустимые зависимости определяет проект**

    Проект сам определяет, какие зависимости между его слоями являются допустимыми.

    Если конкретная зависимость нарушает общепринятое направление зависимостей, это не делает её
    автоматически ошибкой. Она может быть необходимой особенностью архитектуры конкретного проекта.

    Важно, чтобы такая зависимость была осознанным решением, а не случайным результатом реализации.

3. **Отступление от направления записывается повтором слоя**

    ::: warning Внимание!

    Крайне не рекомендуется повторять слои: это уменьшает гарантии.

    Ответственность за повтор лежит на проекте: только он знает, временный это миграционный мост,
    стабильная часть архитектуры или ошибка в размещении кода.

    :::

    По умолчанию каждый слой встречается в списке один раз, и импорт разрешён только из слоёв левее.
    Повтор имени превращает слой в промежуток между первым и последним вхождением: слой становится
    двунаправленным со всем, что в этот промежуток попало. Смежный повтор (`entities, entities`)
    открывает только горизонтальные связи — между одноимёнными слоями разных директорий.

    Повтор — не «настройка строгости», а заявление о снятой гарантии: внутри промежутка снова
    возможны взаимные зависимости и циклы. Зато размер послабления виден в той же схеме, где записан
    сам порядок, и измеряется расстоянием между вхождениями: миграция выражается их сдвигом
    навстречу друг другу, а закрытый долг — удалением повтора из списка.

## Почему

Самостоятельное определение слоёв даёт конкретные практические выгоды:

- **Соответствие архитектуре проекта**

    Слои отражают реальные границы системы и её ответственность, а не абстрактный архитектурный
    шаблон.

- **Отсутствие искусственных границ**

    Не требуется выделять отдельный слой только потому, что он предусмотрен некоторой методологией.
    Граница появляется тогда, когда она имеет значение для конкретного проекта.

- **Эволюция архитектуры**

    По мере изменения проекта состав слоёв может изменяться вместе с ним. Добавление, объединение
    или разделение слоёв является нормальным архитектурным изменением.

- **Осознанные исключения**

    Архитектура может содержать зависимости, необходимые именно этому проекту. Они не считаются
    ошибкой только из-за несоответствия универсальному правилу.

## Примеры

**Минимальный набор слоёв:**

```text
common
entities
widgets
pages
app
```

Для нового проекта, у которого ещё нет сформировавшихся архитектурных требований, этого набора может
быть достаточно.

**Добавление слоя при появлении новой архитектурной границы:**

<!-- Схема слоёв — не код, поэтому её блоки размечены как `text`. Там, где строка помечена
маркером VitePress (`// [!code ++]`, `// [!code error]`), фенс назван `cpp`: маркер живёт в
комментарии, а убирает комментарий из вывода только подсветка языка, который их знает. Имя языка
здесь — плата за то, чтобы в схеме было видно, какая строка добавлена, а какая лишняя. -->

```cpp
common
entities
features // [!code ++]
widgets
pages
app
```

`features` появляется не потому, что он является обязательным слоем, а потому что в проекте
появилась самостоятельная ответственность, которую имеет смысл выделить в отдельную границу.

**Другой состав слоёв:**

```text
common
entities
features
pages
app
```

В другом проекте `features` может быть необходимой архитектурной границей, тогда как `widgets` не
требуется выделять отдельно.

**Слой без самостоятельной ответственности:**

```cpp
common
entities
features // [!code error]
widgets
pages
app
```

Если `features` добавлен только потому, что он присутствует в используемом архитектурном шаблоне, но
в проекте нет причины выделять его отдельно, такой слой не нужен.

Таким образом, один и тот же слой может быть необходим в одном проекте и не иметь смысла в другом.

**Осознанное отступление, записанное повтором:**

```cpp
common
legacy // [!code ++]
entities
features
widgets
legacy // [!code ++]
pages
app
```

`legacy` объявлен дважды, поэтому он двунаправлен со всем, что попало между вхождениями: старый код
может тянуть `entities`, `features` и `widgets`, а они — его. Это и есть размер снятой гарантии: он
виден прямо в схеме и сокращается по мере того, как вхождения сдвигаются навстречу друг другу.

## Рекомендации

1. **Начинайте с минимального набора**

    Если пока нет понимания, какие слои выделить, например в новом проекте, лучше использовать
    минимальный стандартный набор:

    | Слой     | Назначение                                                       |
    | -------- | ---------------------------------------------------------------- |
    | common   | Переиспользуемый код: uikit, библиотеки                          |
    | entities | Модели и их представление в интерфейсе                           |
    | widgets  | Большие самодостаточные блоки                                    |
    | pages    | Страницы                                                         |
    | app      | Всё, что касается приложения целиком: Провайдеры, создание стора |

    Он даёт базовые архитектурные границы без необходимости заранее придумывать структуру,
    потребность в которой ещё не подтверждена проектом.

2. **Документируйте слои проекта**

    **Всегда** документируйте слои проекта, даже если это стандартные слои. Так будет легко
    подправить требования к слою. В идеале, всегда должно быть понятно к каком слою отнести тот или
    иной код

3. **Добавляйте слой при появлении самостоятельной ответственности**

    Новый слой стоит выделять тогда, когда существующие границы перестают достаточно хорошо
    описывать структуру проекта. Не следует создавать слой заранее только на случай будущего роста.

4. **Не путайте принцип с конкретной реализацией**

    Архитектурный принцип может быть общим, а его реализация — различаться от проекта к проекту.
    Конкретный набор слоёв не является обязательной реализацией этого принципа.
