# Вложенные модули

Когда модуль разрастается, его можно разделить на более мелкие части, сохранив их в пределах
исходного модуля.

В WELD для этого предусмотрены вложенные модули. Они позволяют развивать внутреннюю структуру
приложения, не превращая каждую новую область ответственности в модуль верхнего уровня.

Вложенность влияет не только на организацию кода, но и на доступность модулей друг для друга.
Рассмотрим, как устроено дерево модулей и какие правила определяют взаимодействие между его узлами.

## Фрактальность дерева модулей

Модули могут содержать вложенные (или дочерние) модули, а те — свои вложенные модули. При этом на
каждом уровне действует одна и та же архитектурная модель.

Модули которые выше по дереву или в другой ветке называются внешними.

Например, в системе управления обучением модуль `courses` может содержать уроки и материалы курса, а
каждый урок — упражнения:

```text
modules/
├── courses/
│   └── modules/
│       ├── lessons/
│       │   └── modules/
│       │       └── exercises/
│       └── materials/
└── students/
```

Вложенные модули размещаются в отдельной поддиректории родительского модуля, например `modules/`.
Она служит только контейнером: не является модулем сама по себе, не имеет собственных слоёв и
публичного API. Имя контейнера определяется проектом.

Такое разделение позволяет отличать вложенные модули от остальных частей родительского модуля и не
смешивать разные структурные сущности на одном уровне.

Если `exercises` со временем разрастётся, его тоже можно разделить на вложенные модули. Для этого не
требуется вводить новые архитектурные сущности или специальные правила для отдельных уровней дерева.

Это свойство называется **фрактальностью**: структура повторяется на разных уровнях, а вложенные
модули подчиняются тем же правилам, что и модули верхнего уровня.

Фрактальность позволяет развивать внутреннюю структуру приложения постепенно, не усложняя саму
архитектурную модель.

## Видимость определяется иерархией

Вложенность определяет не только расположение модулей, но и то, какие модули могут обращаться друг к
другу.

Модулю доступны его родительские модули, братья и братья его родителей. При этом сохраняются
ограничения, заданные порядком архитектурных слоёв.

Рассмотрим ту же структуру:

```text
modules/
├── courses/
│   └── modules/
│       ├── lessons/
│       │   └── modules/
│       │       └── exercises/
│       └── materials/
└── students/
```

Модуль `exercises` вложен в `lessons`, а `lessons` и `materials` — соседние модули внутри `courses`.
Поэтому `exercises` может обращаться к публичным точкам входа `lessons`, `materials` и `courses`,
если это допускает порядок слоёв.

При этом доступ к `materials` не означает доступ ко всем его внутренностям: вложенные модули
`materials` не становятся автоматически доступными для `exercises`.

Так дерево модулей ограничивает область взаимодействия. Внутренние части одной ветки не становятся
общедоступными для остальных веток, а зависимости отражают структуру приложения.

## Каждый модуль публикует собственный API

Видимость модуля не означает, что его внутренние файлы доступны для импорта. Как и у модулей
верхнего уровня, у вложенных модулей есть собственные публичные точки входа.

Например, модуль `lessons` использует учебные материалы из соседнего модуля `materials`. Для этого
он обращается к публичной точке входа `materials`:

```ts
import { CourseMaterial } from '@/modules/courses/modules/materials';
```

Модуль `lessons` использует опубликованный интерфейс `materials`, не обращаясь напрямую к его
внутренним файлам.

Вложенный модуль не обязан передавать свой API через родительский модуль. Если `exercises` публикует
собственную точку входа, к ней можно обращаться напрямую — при условии, что такой импорт разрешён
правилами видимости и порядком слоёв.

Таким образом, архитектурные границы определяются двумя независимыми ограничениями:

- **Иерархия модулей** определяет, к каким модулям разрешено обращаться.
- **Публичные точки входа** определяют, к каким частям доступного модуля разрешено обращаться.

Вместе эти правила позволяют дробить крупные модули на вложенные части, не раскрывая их внутреннюю
реализацию всему приложению.

## Правила

1. Вложенные модули размещаются в отдельной поддиректории.

Для размещения вложенных модулей используется отдельная поддиректория родительского модуля, например
`modules/`. Она служит только контейнером: не является модулем сама по себе, не имеет собственных
слоёв и публичного API. Имя контейнера определяется конфигурацией проекта.

Корень проекта устроен похожим образом: он содержит поддиректорию `modules/` с модулями верхнего
уровня. Однако сходство ограничивается организацией дерева — корень проекта не является модулем
WELD.

2. Видимость модулей определяется их положением в дереве.

Модулю доступны его родительские модули, братья, братья его родителей и непосредственные дети.
Остальные модули дерева недоступны.

3. Правило порядка слоёв одинаково применяется ко всем модулям.

Правило порядка слоёв одинаково применяется ко всем модулям, в том числе вложенным.

:::Исключение

Родительский модуль может обращаться к непосредственному дочернему модулю, даже если они находятся
на одном слое.

:::

4. Каждый модуль публикует собственный API.

Вложенный модуль предоставляет публичную точку входа независимо от родительского модуля. Обращение к
нему выполняется через эту точку входа, а не через внутренние файлы.

## Рекомендации

Желательно избегать глубокой вложенности: в большинстве случаев достаточно двух уровней. Более
глубокая структура оправдана только при необходимости выделить устойчивые внутренние границы и
сохранить читаемость дерева модулей. Не следует создавать дополнительные уровни ради технической
группировки файлов.
