# Настройки: `settings.weld`

Настройки секции `settings.weld` общие для всех правил плагина; здесь же описан способ
переопределить их опциями конкретного правила.

```js
export default [
    {
        settings: {
            weld: {
                repoRoot: '.', // необязательно; по умолчанию — авто-поиск
                aliasesBaseUrl: 'packages/app', // необязательно; по умолчанию '.'
                aliases: { '@/*': ['src/*'] },
            },
        },
    },
];
```

## `repoRoot`

Определяет корень репозитория, от которого строятся виртуальные пути.

- Если задан — берётся как есть; **относительное значение резолвится от `context.cwd`** (запуска
  ESLint), а не от расположения конфигурационного файла. Значение, не являющееся строкой, — ошибка.
- Если не задан — выполняется автопоиск: подъём от `context.cwd` вверх, ищется **самый верхний**
  `package.json` (обычно принадлежащий корню монорепы), а подъём останавливается на первой
  директории с `.git` (включительно — её `package.json` ещё учитывается) либо на корне файловой
  системы, если `.git` не встретился.
- Если автопоиск ничего не нашёл (нет ни одного `package.json` по пути наверх) — корнем молча
  становится сам `context.cwd`: отсутствие `package.json` — законная ситуация, ошибки нет.

Результат автопоиска кэшируется по `cwd` без TTL (в рамках жизни процесса ESLint смена корня
репозитория не ожидается).

## `aliasesBaseUrl`

Аналог `baseUrl` из `tsconfig`: задаёт базу, от которой отсчитываются якоря `aliases`. Больше ни на
что не влияет — отсюда и имя.

В отличие от `tsconfig`, где `baseUrl` отсчитывается от расположения самого `tsconfig.json`, здесь
**`aliasesBaseUrl` отсчитывается от корня репозитория (`repoRoot`)**, а не от `context.cwd` и не от
файла конфигурации ESLint. Это осознанное отклонение: при авто-найденном `repoRoot` результат
линтинга не должен зависеть от того, из какой директории запущен ESLint. По умолчанию — `'.'` (сам
`repoRoot`). Значение, не являющееся строкой, — ошибка (как и у `repoRoot`).

## `aliases`

Формат записи совпадает с `paths` из `tsconfig.json` — объект «префикс → один или несколько путей»,
но со следующими отличиями от tsconfig-конвенции:

- значение записи может быть **строкой**, не только массивом (частая опечатка с однозначным смыслом
  — принимается намеренно);
- специфайер подходит под запись, если равен префиксу целиком **или** начинается с `prefix + '/'` —
  **включая записи без `*`**. Это отход от tsconfig, где беззвёздочная запись матчится только на
  точное совпадение: например, `@pkg` (без `/*`) в этом правиле разрешает и `@pkg/internal/thing` —
  ровно тот способ обойти баррель, который правило должно ловить.

Нормализация каждой записи (обе стороны — ключ и значение — обрабатываются независимо):

| запись                                  | префикс | якорь                     | почему                                                         |
| --------------------------------------- | ------- | ------------------------- | -------------------------------------------------------------- |
| `'@/*': ['src/*']`                      | `@`     | `<base>/src`              | хвост `/*` снят с обеих сторон                                 |
| `'@pkg': ['packages/pkg/src/index.ts']` | `@pkg`  | `<base>/packages/pkg/src` | базовое имя `index` с известным расширением → взята директория |
| `'@cfg': ['src/config.ts']`             | `@cfg`  | — (запись отбрасывается)  | обычный файл директорией не выражается                         |
| `'@dir': ['src/dir']`                   | `@dir`  | `<base>/src/dir`          | как есть, без изменений                                        |

где `<base>` — виртуальный путь `resolvePath('/', aliasesBaseUrl ?? '.')`.

Прочие правила разбора:

- значения-массивы разворачиваются в отдельные записи `{ prefix, anchor }`; дубликаты
  `prefix + anchor` схлопываются;
- при разборе импорта выигрывает самый длинный подходящий префикс; при равных длинах — та запись,
  что объявлена раньше;
- при построении исправленного пути выигрывает запись с самым длинным якорем, покрывающим найденную
  границу;
- принимаются только ключи и якоря без `*` либо с хвостом `/*`; звёздочка в середине записи — запись
  отбрасывается; запись `'*'` отбрасывается принудительно (пустой префикс сломал бы отсев голых
  пакетов из `node_modules`);
- ошибки валидации: `aliases` — не объект, значение записи — не строка и не массив, элемент массива
  — не строка. Во всех случаях бросается исключение с текстом, называющим конкретный ключ и место
  значения в конфиге (`settings.weld.aliases['@bad']`).

## Приоритет источников алиасов

Алиасы берутся из первого источника, где они заданы:

1. `aliases` в опциях правила (`options.aliases`);
2. `settings.weld.aliases`;
3. автопоиск — `compilerOptions.paths` ближайшего к линтуемому файлу `tsconfig.json` (см. ниже).

«Заданы» — это присутствие ключа: **пустой объект `{}` тоже считается** и полностью выключает
автопоиск. Модель простая: явные алиасы (даже пустые) — воля пользователя, tsconfig читается только
тогда, когда пользователь про алиасы не сказал ничего. Отдельной настройки для управления
автопоиском нет.

## Автопоиск алиасов из tsconfig

Если явных алиасов нет, плагин ищет `tsconfig.json` вверх от директории линтуемого файла (ближайший
побеждает) и берёт из него `compilerOptions.paths`:

- `extends` резолвится полностью — включая цепочки, массивы и extends в пакет из `node_modules`;
  поддерживаются JSONC (комментарии, висячие запятые) и подстановка `${configDir}`;
- записи `paths` отсчитываются **по tsconfig-семантике**: от `baseUrl` конфига (с учётом `extends`),
  а если `baseUrl` не задан — от директории того конфига, который объявил `paths` (при `extends` это
  может быть база, а не найденный tsconfig — как в TypeScript). Это отличается от
  `settings.weld.aliases`, где `aliasesBaseUrl` отсчитывается от `repoRoot`: у явных алиасов база —
  наша настройка, у tsconfig-овских — его собственная;
- `settings.weld.aliasesBaseUrl` (и `options.aliasesBaseUrl`) на автопоиск **не влияет** — он
  относится только к явным алиасам; база tsconfig-овских записей приходит из самого tsconfig;
- результат поиска кэшируется по директории файла с TTL 10 минут: правка `paths` в долгоживущем
  редакторе подхватится после истечения TTL.

### Инвариант `repoRoot` и подъём при автоопределении

Корень репозитория обязан покрывать якоря всех алиасов: якорь выше него означал бы молча
неработающий алиас и пропущенные нарушения. Отсюда два режима:

- **`repoRoot` автоопределяется** — итоговый корень поднимается до общей директории результата
  автопоиска (см. [`repoRoot`](#reporoot)) и всех якорей записей `paths` (якоря внутри
  `node_modules` в расчёте не участвуют; якорь без общего префикса — например, на другом
  Windows-диске — игнорируется с debug). Следствие: в монорепе разные линтуемые файлы могут найти
  разные tsconfig и получить разный корень — это ожидаемо, виртуальные пути каждого файла
  согласованы со своим корнем. Обратная сторона: при автоопределении подъём не ограничен
  репозиторием — случайный `tsconfig.json` с `paths` **выше** репозитория (например, в домашней
  директории) поднимет корень выше `.git` и подставит свои алиасы. Защита от такого — задать
  `repoRoot` явно;
- **`repoRoot` задан явно** (`settings.weld.repoRoot` или `options.repoRoot`) — он побеждает:
  tsconfig, найденный **вне** явного корня, отбрасывается целиком (иначе результат линтинга зависел
  бы от содержимого директорий над корнем), а якорь выше корня отбрасывается той же валидацией, что
  и у явных алиасов.

### Ошибки tsconfig не валят линт

Любая проблема самого tsconfig — файл не нашёлся, не распарсился, нет `compilerOptions.paths`,
кривые значения `paths`, база записей оказалась вне root — приводит к одному и тому же: алиасов из
tsconfig просто нет, линт продолжает работать, причина уходит в debug (namespace
`eslint-plugin-weld:tsconfig`; отсев уже найденного tsconfig — `eslint-plugin-weld:rules`; подъём
root ради якорей — `eslint-plugin-weld:fs`):

```sh
DEBUG=eslint-plugin-weld:* npx eslint .
```

Это осознанное отличие от явных `settings.weld.aliases`/`options.aliases`, где кривое значение —
громкое исключение: за явный конфиг отвечает пользователь плагина, а tsconfig может принадлежать
кому-то ещё.

## `repoRoot`, `aliasesBaseUrl`, `aliases` в опциях правила

Это те же самые настройки, что и в `settings.weld` (формат, значения по умолчанию и правила разбора
— из разделов выше), но заданные на самом правиле. Заданная опция целиком заменяет одноимённое поле
секции; незаданная — не влияет ни на что, читается `settings.weld`.

Зачем: `settings` в flat config задаются на конфигурационный объект целиком и общие для всех правил,
а опции — на конкретное правило в конкретном блоке `files`. Это способ пролинтовать часть монорепы с
другим `repoRoot` или другим набором алиасов, не заводя отдельную секцию `settings` (и не сбивая её
остальным правилам):

```js
export default [
    {
        settings: { weld: { repoRoot: '.', aliases: { '@/*': ['src/*'] } } },
        rules: { 'weld/no-barrel-bypass': 'error' },
    },
    {
        files: ['legacy/**'],
        rules: {
            'weld/no-barrel-bypass': [
                'error',
                {
                    repoRoot: './legacy',
                    aliasesBaseUrl: 'src',
                    aliases: { '@legacy/*': ['app/*'] },
                },
            ],
        },
    },
];
```

`aliasesBaseUrl` действует и на алиасы из `settings.weld`: якоря считаются от того `aliasesBaseUrl`,
который победил, — переопределить одни только алиасы, оставив им чужую базу, было бы ловушкой.

Значения опций проверяются тем же слоем, что и `settings.weld` (типы полей — ещё и схемой ESLint); в
тексте ошибки источник называется как `options.<имя>` вместо `settings.weld.<имя>`.
