# `weld/no-illegal-layer-dependency`

Запрещает импорты, идущие против направления зависимостей: слой может импортировать только то, что
стоит в схеме проекта левее его самого.

Правило проверяет идею [«Однонаправленность зависимостей»](../core-concepts/direction.md): набор и
порядок слоёв при этом задаёт сам проект (см. [«Слои задаёт проект»](../core-concepts/layers.md)), а
модульные слои повторяются внутри каждого модуля на любой глубине.

Правило входит в `configs.recommended` и `configs.strict`, но схемы по умолчанию у плагина нет и
быть не может — её задаёт проект. Поэтому оба пресета требуют `settings.weld.layers`: без схемы
прогон падает на первом же файле — см. [«Подключение»](#подключение).

## Что проверяется

Правило разбирает каждый импорт и сравнивает слой файла со слоем цели импорта. Формы, в которых
зависимость записывается:

- `import ... from '...'` (включая `import type ... from '...'`);
- `import('...')` со строковым литералом аргумента;
- `require('...')` со строковым литералом аргумента;
- `import x = require('...')` — TypeScript-форма того же `require`, включая запись с модификатором
  (`export import x = require('...')`);
- `export ... from '...'` и `export * from '...'` — реэкспорт.

Реэкспорт проверяется наравне с импортом, и этим список отличается от
[`no-barrel-bypass`](./no-barrel-bypass.md), где реэкспорты не обходятся. Причина у каждого правила
своя: баррель собран из реэкспортов, и соседнее правило репортило бы сам баррель, — а для
направления зависимостей реэкспорт это обычное ребро графа. Пропусти его правило, и запрет обходился
бы переписыванием пары `import` + `export` в одну строку. Баррелю слоя и баррелю модуля это ничего
не стоит: `common/index.ts`, собирающий `./ui`, остаётся внутренним импортом одного владельца, а
`modules/order/index.ts`, собирающий свои слои, работает по диапазону `module`. А вот баррель
директории **без** слоя (`shared/index.ts`, собирающий `./a`) получает тот же вердикт, что и любой
другой импорт такого кода: владельца у него нет, и реэкспорт соседнего файла оказывается
горизонтальной связью (см. [«Горизонтальные связи»](#горизонтальные-связи)) — либо
`undeclaredLayer`, если `@unknown` в схеме не объявлен вовсе. Это не особый случай барреля, а общее
правило для кода вне слоёв. `export { x }` без `from` зависимостью не является и не проверяется.

Алиасы путей учитываются: `@/modules/order/entities` и `../../order/entities` — один и тот же слой.
Сообщение об ошибке ставится на строковом литерале пути.

Диск правило не читает: слой и файла, и цели определяется по именам директорий в пути. Существование
цели не проверяется и на вердикт не влияет.

## Схема слоёв

Схему удобнее держать в общей секции `settings.weld`: это описание проекта, а не поведение одной
проверки. Те же три настройки можно задать и [опциями самого правила](#опции-правила) — например,
чтобы пролинтовать часть монорепы по другой схеме.

```js
export default [
    {
        settings: {
            weld: {
                layers: ['common', 'legacy', '@modules', 'legacy', 'pages', 'app'],
                moduleLayers: ['entities', 'features', 'widgets'],
                moduleDir: 'modules', // по умолчанию
            },
        },
    },
];
```

- `layers` — слои проекта слева направо: от самого стабильного к самому изменчивому;
- `moduleLayers` — слои внутри модуля, в том же порядке;
- `moduleDir` — имя директории, в которой лежат модули; по умолчанию `modules`;
- `@modules` — место в порядке, куда встают модульные слои. Не директория: имя директории задаёт
  `moduleDir`;
- `@unknown` — место в порядке для кода, слой которого определить не удалось (см.
  [ниже](#unknown-на-двух-уровнях)). Допустим в обоих списках.

Имена, начинающиеся с `@`, зарезервированы под такие спец-слои — слой проекта так назвать нельзя.
Зарезервированы и два обычных имени, `unknown` и `module`: ими правило называет спец-слои в своих
сообщениях. Формат записи и валидацию этих настроек см. в
[документации настроек](../settings.md#layers-modulelayers-moduledir).

### Развёрнутый порядок

Правило разворачивает схему в один плоский упорядоченный список, и весь вердикт сводится к сравнению
двух позиций в нём. В этом списке у каждого слоя есть квалификатор: слой проекта и одноимённый слой
внутри модуля — разные слои, и различает их именно он.

| квалифицированный слой | что это                                                    |
| ---------------------- | ---------------------------------------------------------- |
| `root:<имя>`           | слой проекта                                               |
| `module`               | модуль как целое — его публичный интерфейс                 |
| `module:<имя>`         | слой внутри модуля                                         |
| `root:unknown`         | код вне модулей, не попавший ни в один слой проекта        |
| `module:unknown`       | код внутри модуля, не попавший ни в один слой этого модуля |

Развёртка поэлементная: `@modules` превращается в `module`, затем в слои модуля, затем **снова** в
`module`; `@unknown` — в `root:unknown` внутри `layers` и в `module:unknown` внутри `moduleLayers`;
прочие имена — в `root:<имя>` и `module:<имя>`. Для схемы выше:

```text
0  root:common
1  root:legacy
2  module
3  module:entities
4  module:features
5  module:widgets
6  module
7  root:legacy
8  root:pages
9  root:app
```

Обрамляющие `module` — не украшение: модуль как целое получает **диапазон** вокруг своих слоёв.
Отсюда без единого особого случая следует, что баррель модуля двунаправлен со слоями модулей (любой
слой модуля вправе импортировать чужой модуль целиком, а модуль вправе импортировать слои модулей),
а до `pages` и `app` не достаёт.

Квалификатор — внутренняя форма записи: в сообщениях правила слои называются так же, как в конфиге
(`entities`, `module`, `@unknown`).

### Почему две настройки, а не один готовый список

Список можно было бы записать сразу развёрнутым. Разделение сохраняет то, что из порядка не
выводится: модульные слои существуют в каждом модуле и на любой глубине вложенности, слои проекта —
в единственном экземпляре. Это разные сущности, и `@modules` показывает одним взглядом, где проходит
граница между ними.

### Повторы: диапазон вместо списка исключений

По умолчанию каждое имя встречается в развёрнутом порядке один раз. Повтор имени превращает слой в
диапазон и расширяет разрешённый граф зависимостей:

- **смежный повтор** (`entities, entities`) — открывает горизонтальные связи: одноимённые слои
  разных владельцев могут импортировать друг друга;
- **разнесённый повтор** (`legacy, …, legacy`) — делает слой двунаправленным со всем, что попало
  между вхождениями.

Повтор — это заявление о снятой гарантии, а не «настройка строгости»: он может сделать возможными
двусторонние связи и циклы внутри диапазона. Зачем такое послабление нужно, чем оно оплачено и как
сужается — решение проекта (см. [«Слои задаёт проект»](../core-concepts/layers.md)). Правило видит
только форму: первое и последнее вхождение имени.

Единственный слой, который получает диапазон сам по себе, — `module`: его обрамляющие вхождения
ставит развёртка `@modules`, а не проект.

## Слой файла и слой цели

Слой — **самая глубокая** директория из схемы на пути. Какие имена при этом значимы, зависит от
того, находится ли путь внутри модуля:

- **внутри модуля** значимы имена из `moduleLayers`;
- **вне модулей** — имена из `layers`.

Списки не смешиваются: имя модульного слоя вне модуля слоем не является, имя слоя проекта внутри
модуля — тоже. Вход в модуль сбрасывает найденный снаружи слой: у модуля своя система слоёв.

Два конца импорта опознаются по-разному:

- у **линтуемого файла** сканируется только его директория: имя файла слоя не заявляет. Ровно одно
  исключение — точка входа прямо в директории модуля (`…/order/index.ts`): она и есть публичный
  интерфейс модуля, поэтому у такого файла слой `module`, а не `module:unknown` (см.
  [«Модули»](#модули));
- у **цели импорта** сканируется путь **как он записан в специфаере**: `@/modules/order` — это
  модуль целиком, и разворачивать его в `…/order/index.ts` нельзя, иначе самый канонический
  легальный импорт — через баррель — оказался бы нарушением.

Цена у обоих решений известна и принята: вложенная папка с именем более высокого слоя расширяет
права файла (`src/common/utils/app/` даёт слой `app`), а файл `common/app.ts`, записанный в
специфаере как `@/common/app`, прочитается как слой `app`. Директория заявляет свой уровень на любой
глубине, и заявление читается буквально.

### Владелец слоя

Вместе со слоем правило запоминает **владельца** — директорию, которой слой принадлежит: саму
директорию слоя, а для модуля как целого и для его неразмеченного кода — директорию модуля. Если
владельцы обоих концов импорта совпали, импорт внутренний и правилу не принадлежит:
`…/entities/bar.ts` → `…/entities/foo/user.ts` — внутреннее дело одной директории слоя.

Владелец `null` (код вне слоёв и вне модулей) общим владельцем не считается: такой код не образует
целого, внутри которого что-то было бы «своим».

### Слой линтуемого файла

Для схемы из примера выше (`moduleDir` — `modules`):

| путь                                            | слой              | владелец                        |
| ----------------------------------------------- | ----------------- | ------------------------------- |
| `/src/common/ui/button.tsx`                     | `root:common`     | `/src/common`                   |
| `/src/common/index.ts`                          | `root:common`     | `/src/common`                   |
| `/src/common/utils/app/format.ts`               | `root:app`        | `/src/common/utils/app`         |
| `/src/shared/lib/x.ts`                          | `root:unknown`    | —                               |
| `/src/index.ts`                                 | `root:unknown`    | —                               |
| `/src/modules/x.ts`                             | `root:unknown`    | —                               |
| `/src/modules/order/index.ts`                   | `module`          | `/src/modules/order`            |
| `/src/modules/order/index.test.ts`              | `module:unknown`  | `/src/modules/order`            |
| `/src/modules/order/lib/x.ts`                   | `module:unknown`  | `/src/modules/order`            |
| `/src/modules/order/pages/x.ts`                 | `module:unknown`  | `/src/modules/order`            |
| `/src/modules/order/entities/index.ts`          | `module:entities` | `/src/modules/order/entities`   |
| `/src/modules/order/entities/user/model.ts`     | `module:entities` | `/src/modules/order/entities`   |
| `/src/modules/order/widgets/card/entities/x.ts` | `module:entities` | `…/order/widgets/card/entities` |
| `/src/modules/order/modules/sub/features/x.ts`  | `module:features` | `…/order/modules/sub/features`  |
| `…/order/widgets/card/modules/sub/index.ts`     | `module`          | `…/card/modules/sub`            |
| `/src/common/modules/x/lib/a.ts`                | `module:unknown`  | `/src/common/modules/x`         |

`/src/modules/x.ts` остаётся вне слоёв, потому что за `modules` нет имени модуля: сама по себе
директория модулей модуля не открывает. `/src/modules/order/pages/x.ts` — тоже: `pages` это слой
проекта, а внутри модуля значимы только `moduleLayers`.

### Слой цели импорта

Специфаеры записаны из файла `…/modules/order/entities/user/x.ts`; путь цели уже разрешён с учётом
алиасов:

| специфаер                  | путь цели               | слой              |
| -------------------------- | ----------------------- | ----------------- |
| `@/common`                 | `/src/common`           | `root:common`     |
| `@/common/index.ts`        | `/src/common/index.ts`  | `root:common`     |
| `@/common/app`             | `/src/common/app`       | `root:app`        |
| `@/modules/order`          | `/src/modules/order`    | `module`          |
| `@/modules/order/index.ts` | `…/order/index.ts`      | `module`          |
| `@/modules/order/lib`      | `…/order/lib`           | `module:unknown`  |
| `@/modules/order/entities` | `…/order/entities`      | `module:entities` |
| `@/modules`                | `/src/modules`          | `root:unknown`    |
| `@/modules/x`              | `/src/modules/x`        | `module`          |
| `..`                       | `…/order/entities`      | `module:entities` |
| `.`                        | `…/order/entities/user` | `module:entities` |

Строка `@/modules/x` — единственное место, где концы импорта читаются по-разному: файл
`/src/modules/x.ts` линтуется как код вне слоёв (за `modules` нет имени модуля — в пути файла
`modules` последний сегмент директории), а тот же файл, записанный в специфаере как `@/modules/x`,
неотличим от барреля модуля `x`. Различить их можно было бы только чтением диска, а правило его не
читает. На практике это значит, что файл прямо в `modules/` лучше не заводить.

### Модули

Модуль — любая поддиректория `moduleDir` (по умолчанию `modules/`). Внутри модуля работают его слои
— те самые `moduleLayers`, одни и те же для всех модулей. Модуль может держать собственный
`modules/`: вложенные модули устроены так же и на любой глубине, разницы между уровнями нет. Модуль
вправе лежать и внутри директории слоя (`…/widgets/card/modules/sub/`) — поиск границы модуля не
прекращается на найденном слое.

- `modules` последним сегментом пути модуля не открывает: `/src/app/modules/x.ts` остаётся слоем
  `app`;
- имя модуля слоем не считается, даже если совпадает с именем слоя: `modules/entities/x.ts` — это
  модуль `entities`, а не слой;
- граница модуля проверяется раньше имён слоёв, поэтому `moduleDir`, совпавший с именем объявленного
  слоя, выигрывает: при `moduleDir: 'modules'` и слое `modules` в схеме `modules/order/` — это
  модуль, а слоем `modules` остаётся только директория без имени модуля за ней;
- публичный интерфейс модуля (`module`) — это сам модуль (`@/modules/order`) либо точка входа прямо
  в его директории (`…/order/index.ts`). Баррель слоя остаётся слоем (`…/order/entities/index.ts` —
  `entities`), а `…/order/lib/index.ts` — внутренность модуля.

Порядок слоёв внутри модуля тот же, что и в схеме, поэтому вложенность не требует отдельных правил:

- `…/order/features/checkout/ui.ts` → `…/checkout/modules/sub/entities/x.ts` — `features` →
  `entities`, разрешено;
- `…/checkout/modules/sub/entities/x.ts` → `…/order/features/other/y.ts` — `entities` → `features`,
  нарушение.

Границу модуля как таковую это правило видит ровно в одном месте — у неразмеченного кода **чужого**
модуля (сообщение `moduleInternals`). Всё остальное про вход внутрь модуля мимо барреля — дело
[`no-barrel-bypass`](./no-barrel-bypass.md).

Опознание модулей по `moduleDir` работает всегда и выключателя не имеет: `@modules` задаёт модулям
место в порядке слоёв, но не включает и не выключает саму границу. Поэтому проект, у которого
`src/modules/` означает что-то своё, получит репорты на этом дереве с обоих концов импорта: файлы
внутри него — `undeclaredLayer` (их слой — модуль, которого в схеме нет), а импорты в него извне —
`undeclaredTargetLayer` с тем же советом объявить `@modules`. Либо объявляйте `@modules`, либо
уводите границу в другое имя (`moduleDir: 'packages'`; имя, которого в дереве нет, и есть способ
отключить модули).

### `@unknown` на двух уровнях

Код, слой которого определить не удалось, есть на каждом уровне, и это два разных слоя:
`root:unknown` вне модулей и `module:unknown` внутри модуля. Объявляются они порознь — `@unknown` в
`layers` и `@unknown` в `moduleLayers`, — и объявить его в обоих списках законно. Само по себе
отсутствие слоя не ошибка: код может быть ещё не разложен, лежать в служебной директории или быть
точкой входа проекта.

Позиция `@unknown` — это и есть ответ на вопрос «что разрешено коду, который ещё не нашёл своего
слоя». Например:

```js
layers: ['common', '@unknown', '@modules', 'pages', 'app'];
```

Такая схема читается так: неразложенный код может брать `common`, модули и страницы могут брать его,
а сам он до модулей, страниц и `app` не дотягивается. Миграция выражается сдвигом этой позиции влево
и, в конце, удалением её из схемы. Повторы работают и здесь: `@unknown, @unknown` открывает связи
между такими файлами, не давая им ничего сверх этого.

В сообщениях оба слоя называются одинаково — `@unknown`, как в конфиге. Поэтому у нарушения
направления **между** ними своё сообщение, `illegalDependencyAcrossLevels`: оно называет уровень
каждого конца. Встретиться эти два слоя могут только когда объявлены оба — иначе цель оказывается
слоем вне схемы (см. [ниже](#слои-которого-нет-в-схеме)):

```js
layers: ['common', '@unknown', '@modules', 'pages', 'app'];
moduleLayers: ['@unknown', 'entities', 'features'];
```

При такой схеме файл вне слоёв, импортирующий неразмеченный код модуля, получит

```text
Illegal layer dependency: '@unknown' outside modules must not import from '@unknown' inside a
module. Same name, different layers: they are declared separately in layers and moduleLayers.
```

Обычное сообщение назвало бы оба конца одним именем и прочиталось бы как «слой не может
импортировать сам себя» — при том, что это два разных слоя, стоящих в схеме в разных местах. Других
таких пар не бывает: одно имя на одном уровне — это один и тот же слой, то есть
[горизонталь](#горизонтальные-связи), а обычное имя сразу в обоих списках отвергает
[валидация схемы](../settings.md#layers-modulelayers-moduledir).

Есть асимметрия, принятая осознанно: **источник схлопывается, цель — нет.** Неразмеченный код модуля
как источник всегда получает права модуля целиком (`module`): он часть модуля и вправе импортировать
всё, что вправе модуль. Объявленный `@unknown` в `moduleLayers` управляет только доступом к такому
коду **извне**, то есть целью. Цена: неразмеченный код модуля получает права шире, чем размеченный
(`module` — диапазон, `module:entities` — точка).

### Слой, которого нет в схеме

Если слоя нет в схеме, правило репортит — и делает это по-разному на разных концах импорта.

**Линтуемый файл** без объявленного слоя репортится один раз, на файле целиком (`undeclaredLayer`),
и его импорты дальше не проверяются: прав у такого файла нет вовсе, каждый его импорт оказался бы
нарушением, и сообщение утонуло бы в них.

**Цель импорта** репортится на литерале пути, а форма сообщения зависит от того, что именно не
объявлено:

| цель                                                   | сообщение               | совет                        |
| ------------------------------------------------------ | ----------------------- | ---------------------------- |
| неразмеченный код **чужого** модуля                    | `moduleInternals`       | идти через баррель модуля    |
| неразмеченный код **своего** модуля                    | `undeclaredTargetLayer` | `'@unknown' in moduleLayers` |
| код вне модулей и вне слоёв                            | `undeclaredTargetLayer` | `'@unknown' in layers`       |
| что угодно внутри модуля, когда `@modules` в схеме нет | `undeclaredTargetLayer` | `'@modules' in layers`       |

Свой модуль отделён от чужого потому, что совет у них разный: «иди через баррель» внутри своего же
модуля было бы советом импортировать самого себя, и остаётся разметка.

Последняя строка перекрывает две первых: пока в схеме нет `@modules`, модулей для неё не существует
вовсе, и совет объявить `@unknown` в `moduleLayers` вёл бы в конфиг, который отвергает
[валидация](../settings.md#layers-modulelayers-moduledir) — `moduleLayers` без `@modules` это
ошибка. Первый шаг в такой схеме один и тот же для обоих концов импорта: объявить `@modules`.

Советы в этих сообщениях стоит читать как варианты, а не как готовую правку: `@unknown` в
`moduleLayers` — изменение схемы всего проекта, оно открывает неразмеченные внутренности **каждого**
модуля всем слоям правее объявленной позиции. Локальное решение здесь — разложить код по слоям
модуля или вывести его наружу через баррель; объявлять `@unknown` имеет смысл тогда, когда проект
согласен на такую позицию для неразмеченного кода целиком.

Молчать здесь нельзя: слой не определился — значит направление зависимостей у этого файла не
проверено ничем, а линт при этом зелёный. Ложная безопасность хуже шумного отчёта: непроверенный код
выглядит ровно как проверенный. Выйти из этого состояния можно двумя способами, и оба — решение
проекта, а не правила: положить код в слой либо объявить `@unknown` в схеме и тем самым сказать, что
такому коду позволено. Для файлов, которые в схему не попадают никогда — конфиги сборки, скрипты,
генерация, — область правила ограничивается блоком `files` в flat config.

### Горизонтальные связи

Горизонталь — импорт между **одноимёнными слоями разных владельцев**: `…/order/entities` →
`…/user/entities`. Она запрещена, пока имя не объявлено смежным повтором.

Сообщение сформулировано нейтрально (`must not import from another 'entities'`), потому что условие
— совпадение слоёв при разных владельцах, и оно возможно не только у модулей:

- одноимённые слои проекта, возникшие из-за deepest: `/src/app/main.ts` → `/src/common/utils/app/`;
- два файла вне слоёв при объявленном `@unknown`: владельца у такого кода нет, одним целым он не
  является — горизонталью оказывается **любой** импорт между такими файлами, включая соседний файл
  той же директории (`/src/shared/a.ts` → `./b.ts`). Поэтому сообщение и не говорит «из другой
  директории»: здесь директория та же самая. Реэкспорт не исключение: `shared/index.ts` с
  `export * from './a'` — та же горизонталь, баррель слоя директории не даёт.

Последнее — самая частая форма кода в проекте, который только что объявил `@unknown`, чтобы начать
разметку. Выхода два, и оба — решение проекта: разложить код по слоям либо объявить смежный повтор
`'@unknown', '@unknown'`, который открывает связи между такими файлами, не давая им ничего сверх
этого.

Список, в котором объявляется повтор, сообщение называет прямо (`in layers` либо `in moduleLayers`):
слой модуля повторяется в `moduleLayers`, и тот же повтор в `layers` разбор схемы отверг бы — одно
обычное имя в обоих списках это [ошибка конфига](../settings.md#layers-modulelayers-moduledir).

Что при этом не ограничивается:

- импорты внутри одной директории слоя — у них общий владелец, включая файл, лежащий прямо в
  директории слоя (`entities/index.ts`, `common/config.ts`);
- импорты между неразмеченными файлами одного модуля — общий владелец, директория модуля;
- импорт чужого модуля целиком (`@/modules/user`) — у `module` диапазон, а не точка.

## Что разрешено

Импорт из слоя `A` в слой `B` разрешён тогда и только тогда, когда **первое** вхождение `B` в
развёрнутый порядок стоит строго левее **последнего** вхождения `A`. Перед этим сравнением есть один
пропуск — общий владелец (внутренний импорт), и одно приведение — права неразмеченного кода модуля
считаются правами `module`.

Для схемы из примера выше:

| слой       | может импортировать                                                      |
| ---------- | ------------------------------------------------------------------------ |
| `common`   | —                                                                        |
| `legacy`   | `common`, `legacy`, `module`, `entities`, `features`, `widgets`          |
| `module`   | `common`, `legacy`, `module`, `entities`, `features`, `widgets`          |
| `entities` | `common`, `legacy`, `module`                                             |
| `features` | `common`, `legacy`, `module`, `entities`                                 |
| `widgets`  | `common`, `legacy`, `module`, `entities`, `features`                     |
| `pages`    | `common`, `legacy`, `module`, `entities`, `features`, `widgets`          |
| `app`      | `common`, `legacy`, `module`, `entities`, `features`, `widgets`, `pages` |

Отсюда свойства, на которые можно рассчитывать:

- слой без повтора не может импортировать одноимённый слой другого владельца — горизонтальные связи
  закрыты, пока проект не объявил их смежным повтором;
- `module` — всегда диапазон, поэтому баррели модулей двунаправлены и между собой, и со слоями
  модулей; при этом права модуля не дотягиваются до слоёв, **первое вхождение** которых правее
  `@modules` (`legacy` в таблице выше модулям доступен: его первое вхождение — левее);
- повтор раздвигает права самого слоя в обе стороны диапазона, но не даёт слоям внутри диапазона
  новых прав друг на друга: `legacy` двунаправлен с `entities` и `features`, а `entities` от этого
  не получает права импортировать `features`;
- самый левый слой схемы не может импортировать ничего за пределами собственной директории. Нужны
  горизонтальные связи внутри него — это записывается как `common, common`.

## Примеры

Дано дерево (слои — из примера выше, алиас `'@/*': ['src/*']`):

```text
src/
├── 🛠️ common/
│   └── ui/
├── 🦖 legacy/
│   └── api/
├── modules/
│   ├── 🗂️ order/
│   │   ├── index.ts
│   │   ├── lib/
│   │   ├── 📦 entities/
│   │   │   ├── order/
│   │   │   └── status/
│   │   ├── ✨ features/
│   │   │   └── checkout/
│   │   └── 🖼️ widgets/
│   │       └── card/
│   └── 🗂️ user/
│       ├── index.ts
│       └── 📦 entities/
│           └── user/
├── 📄 pages/
│   └── checkout/
└── 🚀 app/
```

Valid:

```ts
// src/modules/order/features/checkout/model.ts — features → entities своего модуля
import { Order } from '@/modules/order/entities/order';

// src/modules/order/features/checkout/model.ts — features → баррель чужого модуля
import { user } from '@/modules/user';

// src/modules/order/widgets/card/ui.tsx — widgets → legacy
import { legacyRequest } from '@/legacy/api';

// src/legacy/api/client.ts — legacy → entities, разнесённый повтор legacy
import { Order } from '@/modules/order/entities/order';

// src/modules/order/entities/order/ui.tsx — внутри одной директории слоя
import { OrderStatus } from '../status/ui';

// src/common/index.ts — файл в директории слоя собирает его содержимое
import { Button } from './ui';

// src/pages/checkout/index.ts — pages → баррель слоя
import { Button } from '@/common';
```

Invalid:

```ts
// src/modules/order/entities/order/ui.tsx
import { Checkout } from '@/modules/order/features/checkout';
// Illegal layer dependency: 'entities' must not import from 'features'.

// src/modules/order/entities/order/model.ts
import { User } from '@/modules/user/entities/user';
// Illegal layer dependency: 'entities' must not import from another 'entities'.
// Declare 'entities' twice in a row in moduleLayers to allow horizontal imports.

// src/common/ui/button.tsx
import { Order } from '@/modules/order/entities/order';
// Illegal layer dependency: 'common' must not import from 'entities'.

// src/legacy/api/client.ts
import { CheckoutPage } from '@/pages/checkout';
// Illegal layer dependency: 'legacy' must not import from 'pages'.

// src/pages/checkout/ui.tsx
import { format } from '@/modules/order/lib/format';
// 'pages' must not import internals of another module: '@/modules/order/lib/format' has no layer
// inside its module. Import through the module barrel, or declare '@unknown' in moduleLayers.

// src/modules/order/features/checkout/model.ts
import { formatDate } from '@/shared/date';
// '@/shared/date' belongs to '@unknown', which is not declared in the layer schema.
// Move it into a layer, or declare '@unknown' in layers.
```

Предпоследний пример — про размер послабления: разнесённый повтор `legacy` открывает диапазон до
`widgets`, но `pages` и `app` остаются правее обоих вхождений и легаси-коду недоступны.

Сам файл `src/shared/date.ts` при этой схеме получит своё сообщение, и не на импорте, а на файле
целиком:

```text
This file belongs to '@unknown', which is not declared in the layer schema.
Move the file into a layer, or declare '@unknown' in layers.
```

## Сообщения

| `messageId`                     | текст                                                                                                                                                                                           |
| ------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `illegalDependency`             | `Illegal layer dependency: '{{fromLayer}}' must not import from '{{toLayer}}'.`                                                                                                                 |
| `illegalDependencyAcrossLevels` | `Illegal layer dependency: '{{fromLayer}}' {{fromLevel}} must not import from '{{toLayer}}' {{toLevel}}. Same name, different layers: they are declared separately in layers and moduleLayers.` |
| `horizontalDependency`          | `Illegal layer dependency: '{{layer}}' must not import from another '{{layer}}'. Declare '{{layer}}' twice in a row in {{list}} to allow horizontal imports.`                                   |
| `undeclaredLayer`               | `This file belongs to '{{layer}}', which is not declared in the layer schema. Move the file into a layer, or declare {{declare}}.`                                                              |
| `undeclaredTargetLayer`         | `'{{target}}' belongs to '{{layer}}', which is not declared in the layer schema. Move it into a layer, or declare {{declare}}.`                                                                 |
| `moduleInternals`               | `'{{fromLayer}}' must not import internals of another module: '{{target}}' has no layer inside its module. Import through the module barrel, or declare '@unknown' in moduleLayers.`            |

`{{target}}` — специфаер, как он записан в исходнике. Слои в сообщениях называются простыми именами
— теми же, что в конфиге; квалификатор не показывается:

| квалифицированный слой           | в сообщении |
| -------------------------------- | ----------- |
| `root:<имя>`, `module:<имя>`     | `<имя>`     |
| `module`                         | `module`    |
| `root:unknown`, `module:unknown` | `@unknown`  |

Последняя строка — единственное место, где простого имени не хватает: два разных слоя называются
одинаково. Поэтому нарушение между ними идёт отдельным сообщением с уровнем каждого конца
(`outside modules` / `inside a module`) — см.
[«`@unknown` на двух уровнях»](#unknown-на-двух-уровнях). Во всех остальных парах имена различаются:
одинаковое имя на одном уровне — это один и тот же слой, а одно обычное имя в обоих списках схема не
принимает.

Горизонтальная связь получает своё сообщение, потому что подсказка у неё другая: слой сам себе не
разрешён, и решается это либо переносом кода, либо смежным повтором в схеме — не тем же, чем обычное
нарушение направления; список для повтора сообщение называет прямо, потому что повтор слоя модуля в
`layers` схема отвергла бы. Сообщения про необъявленный слой разделены по той же причине: в одном
случае переезжать или объявляться должен сам линтуемый файл, в другом — цель импорта, и указать на
неё можно только по имени; `moduleInternals` отделён от них потому, что его исправляют не разметкой,
а импортом через баррель.

Когда слой объявлен в схеме, сообщений про необъявленный слой не бывает вовсе: код без слоя получает
`@unknown` и дальше фигурирует в обычных сообщениях под этим именем — тем же, что и в схеме.

## Исправлений правило не предлагает

Ни автофикса, ни подсказки: нарушение направления не исправляется правкой пути. Правильный ответ —
перенести код в другой слой, развернуть зависимость через абстракцию или осознанно изменить схему.
Ни одно из этих решений не механическое, и предлагать здесь автозамену значило бы предлагать
неверную правку.

## Настройки: `settings.weld`

Правило читает `layers`, `moduleLayers` и `moduleDir` (схема слоёв), а также общие настройки плагина
— `repoRoot`, `aliasesBaseUrl`, `aliases`; если алиасы не заданы явно, они подхватываются из
ближайшего к линтуемому файлу `tsconfig.json`. Формат всех настроек, их валидация и приоритет
источников алиасов описаны в [документации настроек](../settings.md).

## Опции правила

```js
{
    rules: {
        'weld/no-illegal-layer-dependency': ['error', {
            layers: ['common', '@modules', 'pages', 'app'],
            moduleLayers: ['entities', 'features'],
        }],
    },
}
```

Схема опций — один объект (лишние ключи запрещены):

| опция            | тип        | по умолчанию                                                                                                                    |
| ---------------- | ---------- | ------------------------------------------------------------------------------------------------------------------------------- |
| `layers`         | `string[]` | значение `settings.weld.layers`                                                                                                 |
| `moduleLayers`   | `string[]` | значение `settings.weld.moduleLayers`                                                                                           |
| `moduleDir`      | `string`   | значение `settings.weld.moduleDir`, иначе `'modules'`                                                                           |
| `repoRoot`       | `string`   | значение `settings.weld.repoRoot`                                                                                               |
| `aliasesBaseUrl` | `string`   | значение `settings.weld.aliasesBaseUrl`                                                                                         |
| `aliases`        | `object`   | значение `settings.weld.aliases`, иначе — автопоиск из tsconfig (см. [настройки](../settings.md#автопоиск-алиасов-из-tsconfig)) |

Первые три — собственные опции правила: схему читает только оно, и принимать `layers` в опциях
соседних правил значило бы принимать настройку и молча её игнорировать. Остальные три — общие
настройки плагина, заданные на самом правиле; как они перекрывают секцию, описано в
[документации настроек](../settings.md#reporoot-aliasesbaseurl-aliases-в-опциях-правила).

Заданная опция целиком заменяет одноимённое поле `settings.weld`: `layers` в опции не дописывается к
схеме из секции, а подменяет её. Перекрываются настройки порознь — можно задать опцией `moduleDir`,
оставив `layers` из секции. Практический смысл тот же, что у `repoRoot` в опциях: пролинтовать часть
монорепы по другой схеме, не сбивая секцию `settings` остальным правилам.

Порознь — значит и собираются порознь: незаданные опции по-прежнему читаются из секции, и смешанная
пара может оказаться несовместимой. Если в секции есть `moduleLayers`, а опция `layers` подменяет
схему списком **без** `@modules`, разбор упадёт с
`settings.weld.moduleLayers is set, but options.layers has no '@modules' to put it into` — ошибка
называет настройку, которой пользователь не трогал, и это не опечатка в тексте: `moduleLayers` из
секции действительно остался, а места для него в новой схеме нет. Способа «снять» настройку опцией
нет, поэтому у такого блока два выхода: оставить `@modules` в опции `layers` либо описать блок
отдельной секцией `settings`.

## Подключение

Правило включают оба пресета — `configs.recommended` и `configs.strict`, — а схемы по умолчанию у
плагина нет и быть не может: её задаёт проект. Поэтому подключение любого из пресетов обязывает
задать схему:

```js
import { defineConfig } from 'eslint/config';
import weld from 'eslint-plugin-weld';

export default defineConfig([
    {
        files: ['src/**'],
        extends: [weld.configs.recommended],
        settings: {
            weld: {
                layers: ['common', '@modules', 'pages', 'app'],
                moduleLayers: ['entities', 'features', 'widgets'],
            },
        },
    },
]);
```

Схема здесь обязательна: правило без `layers` роняет прогон ESLint на первом же файле (см.
[поведение в крайних случаях](#поведение-в-краиних-случаях)). Поскольку правило включает сам пресет,
это относится и к тем, кто подключил `weld.configs.recommended` ради одного `no-barrel-bypass`:
схема нужна всем.

Пресет здесь подключён через `extends` **внутри** блока с `files`, и это не косметика. Сам по себе
пресет — обычный объект flat config без `files`, то есть действующий на все линтуемые файлы; схема,
положенная в соседний блок с `files: ['src/**']`, до `eslint.config.js`, `vite.config.ts` и прочего
вне `src/` не доходит — и прогон падает уже на них, хотя схема в конфиге есть. Рабочих вариантов
два:

- подключить пресет через `extends` в блоке со схемой (как выше) — правила и схема получают одну и
  ту же область. Требует ESLint 9.15 или новее и `defineConfig` из `eslint/config`: `extends` в
  голом массиве конфигов ESLint не понимает;
- задать `settings.weld` без `files`, на весь конфиг, — тогда файлы вне слоёв получат
  `undeclaredLayer` вместо падения, и `files` остаётся способом их приглушить.

Область правила сузить стоит в обоих случаях: схема описывает код приложения, а конфиги сборки,
скрипты и генерация в слои не укладываются — каждый такой файл иначе получит `undeclaredLayer`.

## Поведение в крайних случаях

- **Схема не задана** — ни `settings.weld.layers`, ни `options.layers`: правило бросает исключение
  внутри `create()`
  (`weld/no-illegal-layer-dependency requires a layer schema: set settings.weld.layers or options.layers`).
  ESLint такие исключения не репортит, а пробрасывает наружу: прогон падает на первом же файле,
  который попал под правило. Правило включено, а проверять нечем — это неполный конфиг, а не
  разрешение на всё; молча отключившееся правило хуже громко упавшего (тот же принцип, что у
  некорректных `aliases`).
- **Пустая схема** (`layers: []`) — не ошибка конфигурации: ключ задан, просто в схеме нет ни одного
  слоя. Каждый проверяемый файл получает `undeclaredLayer`, импорты не проверяются.
- **Некорректная схема** — то же падение прогона, с указанием места значения
  (`settings.weld.layers[3]` либо `options.layers[3]`). Типы самих опций (`layers` — массив строк,
  `moduleDir` — строка) отсекает схема опций ESLint, и это уже обычная ошибка конфигурации, а не
  падение. Полный список проверок — в
  [документации настроек](../settings.md#layers-modulelayers-moduledir).
- **`@modules` без `moduleLayers`** — не ошибка: развёртка даёт смежный повтор `module, module`, то
  есть модули без внутренних слоёв, которые вправе импортировать друг друга через баррели.
- **Файл вне корня репозитория** — не проверяется, как и в
  [`no-barrel-bypass`](./no-barrel-bypass.md#поведение-в-краиних-случаях). Это решается раньше
  чтения схемы, поэтому на таких файлах не падает и незаданная схема.
- **Файл или цель без объявленного слоя** — нарушение (`undeclaredLayer` на файле,
  `undeclaredTargetLayer` или `moduleInternals` на импорте), а не пропуск: иначе непроверенный код
  выглядел бы проверенным. Служебные файлы, которым слой не нужен, выводятся из области правила
  блоком `files`.
- **Импорт мимо барреля** — слой цели определяется её расположением, поэтому обычный обход барреля
  (`…/widgets/card/lib/internal.ts`) проверяется как импорт из `widgets`. Если же обход залезает во
  вложенный модуль с собственными слоями, слоем цели станет слой этого модуля, и по направлению
  такой импорт может оказаться законным. Правила дополняют друг друга и не заменяют: за границу
  модуля отвечает [`no-barrel-bypass`](./no-barrel-bypass.md).

## Что правило сознательно не проверяет

- существование цели импорта — путь не резолвится на диске: слой читается из имён директорий, и
  несуществующий путь опознаётся так же, как существующий;
- транзитивные зависимости и циклы — каждый импорт проверяется сам по себе; ацикличность
  обеспечивается схемой, а не обходом графа зависимостей;
- инкапсуляцию модуля — вход внутрь модуля мимо барреля ловит
  [`no-barrel-bypass`](./no-barrel-bypass.md); здесь граница модуля видна только у неразмеченного
  кода чужого модуля;
- смысл имён слоёв — для правила это строки: оно не знает, что `entities` про сущности, и не
  возражает против любых других имён;
- обоснованность повтора — миграционный мост и забытое послабление выглядят одинаково; аргумент к
  повтору хранит проект;
- инварианты содержимого слоя (например, «в `types` нет рантайма») — слой определяется расположением
  файла, а не тем, что в нём написано;
- зависимости, не выраженные литеральным специфайером, — динамически собранные пути, строки в
  DI-контейнерах, реестры плагинов;
- импорты не-JS ресурсов, специфайеры с `?`/`!`, голые пакеты и абсолютные пути — тот же список
  исключений, что и в
  [`no-barrel-bypass`](./no-barrel-bypass.md#что-правило-сознательно-не-проверяет).
