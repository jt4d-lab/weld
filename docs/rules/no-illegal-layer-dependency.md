# `weld/no-illegal-layer-dependency`

Запрещает импорты, идущие против направления зависимостей: слой может импортировать только то, что
стоит в схеме проекта левее его самого.

::: warning Правило ещё не реализовано

Страница написана как документация готового правила: всё, что здесь описано, — гарантии, которые
правило обязано давать. До реализации она служит её определением готовности; включать правило в
конфиге пока нельзя, в плагине его нет.

:::

Правило проверяет идею [«Однонаправленность зависимостей»](../core-concepts/direction.md): набор и
порядок слоёв при этом задаёт сам проект (см. [«Слои задаёт проект»](../core-concepts/layers.md)), а
модульные слои повторяются внутри каждого модуля на любой глубине (см.
[«Общие слои и фрактальность модулей»](../core-concepts/fractal-modules.md)).

## Что проверяется

Правило разбирает каждый импорт и сравнивает слой файла со слоем цели импорта. Формы импорта — те
же, что у [`no-barrel-bypass`](./no-barrel-bypass.md):

- `import ... from '...'` (включая `import type ... from '...'`);
- `import('...')` со строковым литералом аргумента;
- `require('...')` со строковым литералом аргумента.

Алиасы путей учитываются: `@/modules/order/entities` и `../../order/entities` — один и тот же слой.
Сообщение об ошибке ставится на строковом литерале пути.

## Схема слоёв

Схема живёт в общих настройках плагина, а не в опциях правила: это описание проекта, а не поведение
одной проверки.

```js
export default [
    {
        settings: {
            weld: {
                layers: ['common', 'legacy', '@modules', 'legacy', 'pages', 'app'],
                moduleLayers: ['entities', 'features', 'widgets'],
                moduleDir: 'modules', // по умолчанию
            },
        },
    },
];
```

- `layers` — слои проекта слева направо: от самого стабильного к самому изменчивому;
- `moduleLayers` — слои внутри модуля, в том же порядке;
- `moduleDir` — имя директории, в которой лежат модули; по умолчанию `modules`;
- `@modules` — место в порядке, куда встают модульные слои. Не директория: имя директории задаёт
  `moduleDir`;
- `@unknown` — место в порядке для файлов, слой которых определить не удалось (см.
  [ниже](#unknown-файлы-без-слоя)).

Имена, начинающиеся с `@`, зарезервированы под такие спец-слои — слой проекта так назвать нельзя.

Итоговый порядок слоёв — один список, в котором `@modules` заменён на `moduleLayers`:

```text
common, legacy, entities, features, widgets, legacy, pages, app
```

Формат записи и валидацию этих настроек см. в
[документации настроек](../settings.md#layers-modulelayers-moduledir).

### Почему две настройки, а не один готовый список

Список можно было бы записать сразу развёрнутым. Разделение сохраняет то, что из порядка не
выводится: модульные слои существуют в каждом модуле и на любой глубине вложенности, слои проекта —
в единственном экземпляре. Это разные сущности, и `@modules` показывает одним взглядом, где проходит
граница между ними.

### Повторы: диапазон вместо списка исключений

По умолчанию каждое имя встречается в схеме один раз. Повтор имени превращает слой в диапазон и
расширяет разрешённый граф зависимостей:

- **смежный повтор** (`entities, entities`) — открывает горизонтальные связи: модули одного слоя
  могут импортировать друг друга, в том числе одноимённые слои разных модулей;
- **разнесённый повтор** (`legacy, …, legacy`) — делает слой двунаправленным со всем, что попало
  между вхождениями.

Повтор — это заявление о снятой гарантии, а не «настройка строгости»: он может сделать возможными
двусторонние связи и циклы внутри диапазона. Зачем такое послабление нужно, чем оно оплачено и как
сужается — решение проекта (см. [«Слои задаёт проект»](../core-concepts/layers.md)). Правило видит
только форму: первое и последнее вхождение имени.

## Слой файла

Слой файла — самая глубокая директория из схемы на его пути. Какие директории считаются слоями,
зависит от того, лежит ли файл в модуле:

- **внутри модуля** значимы имена из `moduleLayers`;
- **вне модулей** — имена из `layers`.

Списки не смешиваются: имя модульного слоя вне модуля слоем не является, имя слоя проекта внутри
модуля — тоже. Файл, не попавший ни в один слой, относится к `@unknown`.

| путь                                                            | слой       | почему                                        |
| --------------------------------------------------------------- | ---------- | --------------------------------------------- |
| `src/common/ui/button.tsx`                                      | `common`   | слой проекта                                  |
| `src/common/index.ts`                                           | `common`   | файл лежит прямо в директории слоя            |
| `src/modules/order/entities/order/model.ts`                     | `entities` | слой модуля `order`                           |
| `src/modules/order/widgets/card/lib/internal.ts`                | `widgets`  | слой модуля, глубина внутри слоя не важна     |
| `src/modules/order/features/checkout/modules/sub/entities/x.ts` | `entities` | слой вложенного модуля `sub`                  |
| `src/entities/user/model.ts`                                    | `@unknown` | `entities` — слой модуля, а модуля в пути нет |
| `src/modules/order/pages/x.ts`                                  | `@unknown` | `pages` — слой проекта, внутри модуля не слой |
| `src/shared/lib/format.ts`                                      | `@unknown` | имени `shared` в схеме нет                    |
| `src/index.ts`                                                  | `@unknown` | файл не лежит ни в одном слое                 |

Имена слоёв заняты во всём дереве: обычную директорию нельзя назвать именем слоя — она будет
прочитана как слой (`src/common/utils/app/` даст слой `app`).

### Модули

Модуль — любая поддиректория `moduleDir` (по умолчанию `modules/`). Внутри модуля работают его слои
— те самые `moduleLayers`, одни и те же для всех модулей. Модуль может держать собственный
`modules/`: вложенные модули устроены так же и на любой глубине, разницы между уровнями нет.

Порядок слоёв внутри модуля тот же, что и в схеме, поэтому вложенность не требует отдельных правил:

- `…/order/features/checkout/ui.ts` → `…/checkout/modules/sub/entities/x.ts` — `features` →
  `entities`, разрешено;
- `…/checkout/modules/sub/entities/x.ts` → `…/order/features/other/y.ts` — `entities` → `features`,
  нарушение.

Слои глобальны для проекта: импорт из другого модуля легален ровно тогда, когда он легален по слоям.
То, что цель лежит в чужом модуле, правило направления не ограничивает — за отношения модулей
отвечает другое правило.

### `@unknown`: файлы без слоя

Файл, для которого слой определить не удалось, относится к слою `@unknown` — так же, как если бы он
лежал в директории с этим именем. Это не ошибка сама по себе: код может быть ещё не разложен по
слоям, лежать в служебной директории или быть точкой входа проекта.

Попадут ли такие файлы под проверку, решает наличие `@unknown` в схеме.

**`@unknown` объявлен в `layers`** — файлы без слоя получают его позицию и участвуют в проверке
наравне с остальными: им разрешено то, что левее, и они доступны тем, у кого стоят левее. Например:

```js
layers: ['common', '@unknown', '@modules', 'pages', 'app'];
```

Такая схема читается так: неразложенный код может брать `common`, модули и страницы могут брать его,
а сам он до модулей, страниц и `app` не дотягивается. Позиция `@unknown` — это и есть ответ на
вопрос «что разрешено коду, который ещё не нашёл своего слоя»; миграция выражается сдвигом этой
позиции влево и, в конце, удалением её из схемы.

Повторы работают и здесь: `@unknown, @unknown` открывает связи между такими файлами, не давая им
ничего сверх этого.

**`@unknown` в схеме нет** — файл без слоя считается нарушением, а не пропуском:

- линтуемый файл без слоя репортится один раз, в начале файла (`unknownLayer`); его импорты дальше
  не проверяются — сравнивать нечего;
- импорт, цель которого без слоя, репортится на литерале пути (`unknownTargetLayer`).

Молчать здесь нельзя: слой не определился — значит направление зависимостей у этого файла не
проверено ничем, а линт при этом зелёный. Ложная безопасность хуже шумного отчёта: непроверенный код
выглядит ровно как проверенный.

Выйти из этого состояния можно двумя способами, и оба — решение проекта, а не правила: положить файл
в слой либо объявить `@unknown` в схеме и тем самым сказать, что такому коду позволено. Для файлов,
которые в схему не попадают никогда — конфиги сборки, скрипты, генерация, — область правила
ограничивается блоком `files` в flat config.

### Горизонтальные связи

Импорт между двумя модулями одного слоя (`entities/order/` → `entities/user/`, в том числе в разных
модулях проекта) — горизонтальная связь. Она запрещена, пока слой не объявлен смежным повтором.

Что при этом не ограничивается:

- импорты внутри одного модуля слоя — модуль не закрыт от самого себя;
- импорты файла, лежащего прямо в директории слоя (`entities/index.ts`, `common/config.ts`), в
  модули этого слоя — такой файл принадлежит самому слою и собирает его содержимое.

## Что разрешено

Импорт из файла слоя `A` в файл слоя `B` разрешён тогда и только тогда, когда **первое** вхождение
`B` в схему стоит строго левее **последнего** вхождения `A`.

Для схемы из примера выше:

| слой       | может импортировать                                            |
| ---------- | -------------------------------------------------------------- |
| `common`   | —                                                              |
| `legacy`   | `common`, `legacy`, `entities`, `features`, `widgets`          |
| `entities` | `common`, `legacy`                                             |
| `features` | `common`, `legacy`, `entities`                                 |
| `widgets`  | `common`, `legacy`, `entities`, `features`                     |
| `pages`    | `common`, `legacy`, `entities`, `features`, `widgets`          |
| `app`      | `common`, `legacy`, `entities`, `features`, `widgets`, `pages` |

Отсюда три свойства, на которые можно рассчитывать:

- слой без повтора не может импортировать сам себя — горизонтальные связи закрыты, пока проект не
  объявил их смежным повтором;
- повтор раздвигает права самого слоя в обе стороны диапазона, но не даёт слоям внутри диапазона
  новых прав друг на друга: `legacy` двунаправлен с `entities` и `features`, а `entities` от этого
  не получает права импортировать `features`;
- самый левый слой схемы не может импортировать ничего, включая соседние модули своего же слоя.
  Нужны горизонтальные связи внутри него — это записывается как `common, common`.

## Примеры

Дано дерево (слои — из примера выше, алиас `'@/*': ['src/*']`):

```text
src/
├── 🛠️ common/
│   └── ui/
├── 🦖 legacy/
│   └── api/
├── modules/
│   ├── 🗂️ order/
│   │   ├── 📦 entities/
│   │   │   └── order/
│   │   │       └── lib/
│   │   ├── ✨ features/
│   │   │   └── checkout/
│   │   └── 🖼️ widgets/
│   │       └── card/
│   └── 🗂️ user/
│       └── 📦 entities/
│           └── user/
├── 📄 pages/
│   └── checkout/
└── 🚀 app/
```

Valid:

```ts
// src/modules/order/features/checkout/model.ts — features → entities
import { Order } from '@/modules/order/entities/order';

// src/modules/order/features/checkout/model.ts — features → entities чужого модуля
import { User } from '@/modules/user/entities/user';

// src/modules/order/widgets/card/ui.tsx — widgets → legacy
import { legacyRequest } from '@/legacy/api';

// src/legacy/api/client.ts — legacy → entities, разнесённый повтор legacy
import { Order } from '@/modules/order/entities/order';

// src/modules/order/entities/order/model.ts — внутри своего модуля
import { format } from './lib/format';

// src/common/index.ts — файл в директории слоя собирает модули слоя
import { Button } from './ui';
```

Invalid:

```ts
// src/modules/order/entities/order/ui.tsx
import { Checkout } from '@/modules/order/features/checkout';
// Illegal layer dependency: 'entities' must not import from 'features'.

// src/modules/order/entities/order/model.ts
import { User } from '@/modules/user/entities/user';
// Illegal layer dependency: 'entities' must not import from another module of the same layer.

// src/common/ui/button.tsx
import { Order } from '@/modules/order/entities/order';
// Illegal layer dependency: 'common' must not import from 'entities'.

// src/legacy/api/client.ts
import { CheckoutPage } from '@/pages/checkout';
// Illegal layer dependency: 'legacy' must not import from 'pages'.
```

Последний пример — про размер послабления: разнесённый повтор `legacy` открывает диапазон до
`widgets`, но `pages` и `app` остаются выше обоих вхождений и легаси-коду недоступны.

## Сообщения

| `messageId`            | текст                                                                                                   |
| ---------------------- | ------------------------------------------------------------------------------------------------------- |
| `illegalDependency`    | `Illegal layer dependency: '{{fromLayer}}' must not import from '{{toLayer}}'.`                         |
| `horizontalDependency` | `Illegal layer dependency: '{{layer}}' must not import from another module of the same layer.`          |
| `unknownLayer`         | `Cannot determine the layer of this file. Move it into a layer or declare '@unknown' in the schema.`    |
| `unknownTargetLayer`   | `Cannot determine the layer of '{{target}}'. Move it into a layer or declare '@unknown' in the schema.` |

Горизонтальная связь получает своё сообщение, потому что подсказка у неё другая: слой сам себе не
разрешён, и решается это либо переносом кода ниже, либо смежным повтором в схеме — не тем же, чем
обычное нарушение направления. Два сообщения про неопределённый слой тоже разделены по подсказке: в
первом случае переезжать должен сам линтуемый файл, во втором — цель импорта, и указать на неё можно
только по имени.

Когда `@unknown` в схеме объявлен, этих двух сообщений не бывает вовсе: файл без слоя получает слой
`@unknown` и дальше фигурирует в обычных сообщениях под этим именем — тем же, что и в схеме.

## Исправлений правило не предлагает

Ни автофикса, ни подсказки: нарушение направления не исправляется правкой пути. Правильный ответ —
перенести код в другой слой, развернуть зависимость через абстракцию или осознанно изменить схему.
Ни одно из этих решений не механическое, и предлагать здесь автозамену значило бы предлагать
неверную правку.

## Настройки: `settings.weld`

Правило читает `layers`, `moduleLayers` и `moduleDir` (схема слоёв), а также общие настройки плагина
— `repoRoot`, `aliasesBaseUrl`, `aliases`; если алиасы не заданы явно, они подхватываются из
ближайшего к линтуемому файлу `tsconfig.json`. Формат всех настроек, их валидация и приоритет
источников алиасов описаны в [документации настроек](../settings.md).

## Опции правила

```js
{
    rules: {
        'weld/no-illegal-layer-dependency': ['error', {
            layers: ['common', '@modules', 'pages', 'app'],
            moduleLayers: ['entities', 'features'],
        }],
    },
}
```

Схема опций — один объект (лишние ключи запрещены). Собственных опций у правила нет, все шесть —
общие настройки плагина, заданные на самом правиле:

| опция            | тип        | по умолчанию                                                                                                                    |
| ---------------- | ---------- | ------------------------------------------------------------------------------------------------------------------------------- |
| `layers`         | `string[]` | значение `settings.weld.layers`                                                                                                 |
| `moduleLayers`   | `string[]` | значение `settings.weld.moduleLayers`                                                                                           |
| `moduleDir`      | `string`   | значение `settings.weld.moduleDir`, иначе `'modules'`                                                                           |
| `repoRoot`       | `string`   | значение `settings.weld.repoRoot`                                                                                               |
| `aliasesBaseUrl` | `string`   | значение `settings.weld.aliasesBaseUrl`                                                                                         |
| `aliases`        | `object`   | значение `settings.weld.aliases`, иначе — автопоиск из tsconfig (см. [настройки](../settings.md#автопоиск-алиасов-из-tsconfig)) |

Как опции перекрывают секцию — в
[документации настроек](../settings.md#reporoot-aliasesbaseurl-aliases-в-опциях-правила). Заданная
опция целиком заменяет одноимённое поле `settings.weld`: `layers` в опции не дописывается к схеме из
секции, а подменяет её. Практический смысл тот же, что у `repoRoot` в опциях, — пролинтовать часть
монорепы по другой схеме, не сбивая секцию `settings` остальным правилам.

## Подключение

Правило не входит ни в `configs.recommended`, ни в `configs.strict`: без схемы слоёв проверять
нечего, а схемы по умолчанию у плагина нет и быть не может — её задаёт проект. Включается вручную,
вместе со схемой:

```js
import weld from 'eslint-plugin-weld';

export default [
    weld.configs.recommended,
    {
        files: ['src/**'],
        settings: {
            weld: {
                layers: ['common', '@modules', 'pages', 'app'],
                moduleLayers: ['entities', 'features', 'widgets'],
            },
        },
        rules: { 'weld/no-illegal-layer-dependency': 'error' },
    },
];
```

`files` здесь не формальность: схема описывает код приложения, а конфиги сборки, скрипты и генерация
в слои не укладываются — без ограничения области каждый такой файл получил бы `unknownLayer`.

## Поведение в крайних случаях

- **Схема не задана** — ни `settings.weld.layers`, ни `options.layers`: правило сообщает об ошибке
  конфигурации на каждом проверяемом файле. Правило включено, а проверять нечем — это неполный
  конфиг, а не разрешение на всё; молча отключившееся правило хуже громко упавшего (тот же принцип,
  что у некорректных `aliases`).
- **Некорректная схема** — ошибка конфигурации с указанием места значения (`settings.weld.layers[3]`
  либо `options.layers[3]`). Полный список проверок — в
  [документации настроек](../settings.md#layers-modulelayers-moduledir).
- **`@modules` без `moduleLayers`** — не ошибка: модульных слоёв в схеме просто нет, и слоями внутри
  модулей никто не становится.
- **Файл вне корня репозитория** — не проверяется, как и в
  [`no-barrel-bypass`](./no-barrel-bypass.md#поведение-в-краиних-случаях).
- **Файл или цель без слоя, когда `@unknown` не объявлен** — нарушение (`unknownLayer` на файле,
  `unknownTargetLayer` на импорте), а не пропуск: иначе непроверенный код выглядел бы проверенным.
  Служебные файлы, которым слой не нужен, выводятся из области правила блоком `files`.
- **Импорт мимо барреля** — слой цели определяется её расположением, поэтому обычный обход барреля
  (`…/widgets/card/lib/internal.ts`) проверяется как импорт из `widgets`. Если же обход залезает во
  вложенный модуль с собственными слоями, слоем цели станет слой этого модуля, и по направлению
  такой импорт может оказаться законным. Правила дополняют друг друга и не заменяют: за границу
  модуля отвечает [`no-barrel-bypass`](./no-barrel-bypass.md).

## Что правило сознательно не проверяет

- `export ... from '...'` — реэкспорты не анализируются (как и в `no-barrel-bypass`);
- транзитивные зависимости и циклы — каждый импорт проверяется сам по себе; ацикличность
  обеспечивается схемой, а не обходом графа зависимостей;
- инкапсуляцию модуля — вход внутрь модуля мимо барреля ловит
  [`no-barrel-bypass`](./no-barrel-bypass.md);
- смысл имён слоёв — для правила это строки: оно не знает, что `entities` про сущности, и не
  возражает против любых других имён;
- обоснованность повтора — миграционный мост и забытое послабление выглядят одинаково; аргумент к
  повтору хранит проект;
- инварианты содержимого слоя (например, «в `types` нет рантайма») — слой определяется расположением
  файла, а не тем, что в нём написано;
- зависимости, не выраженные литеральным специфайером, — динамически собранные пути, строки в
  DI-контейнерах, реестры плагинов;
- импорты не-JS ресурсов, специфайеры с `?`/`!`, голые пакеты и абсолютные пути — тот же список
  исключений, что и в
  [`no-barrel-bypass`](./no-barrel-bypass.md#что-правило-сознательно-не-проверяет).
