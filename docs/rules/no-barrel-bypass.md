# `weld/no-barrel-bypass`

Директория, в которой появился файл `index.*`, объявляет себя модулем с публичным API. Правило ловит
импорты, которые входят внутрь такой директории мимо её точки входа, и предлагает исправленный путь
через баррель.

Правило проектно-нейтральное: оно ничего не знает ни про слои, ни про имена директорий. Единственный
источник знания о границах — расположение файлов `index` на диске.

## Что ловит

Для каждого импорта правило ищет **самую верхнюю** директорию на пути от файла с импортом к цели
импорта, у которой есть точка входа (`index.ts`, `index.js` и т. п.). Если такая директория найдена
и цель импорта — не сама эта точка входа, это нарушение.

Проверяются три вида узлов:

- `import` (включая `import type`);
- `import(...)` с строковым литералом;
- `require('...')` — распознаётся синтаксически по имени `require`, без отслеживания затенения
  локальной переменной с тем же именем.

`export … from` **не проверяется** — см. «Что не проверяется» ниже.

### Алгоритм

Обозначения: `F` — файл с импортом, `T` — путь цели, `M` — самая глубокая общая директория
`dirname(F)` и `dirname(T)`, `D` — найденная граница.

1. Строится `M` — общий префикс сегментов `dirname(F)` и `dirname(T)`. Если общего корня нет
   (например, разные диски на Windows) — нарушения нет.
2. Путь от `M` до `T` разбивается на сегменты; последний сегмент (имя файла) в обходе не участвует.
3. Сегменты-директории обходятся сверху вниз, накапливая `D`; на каждой проверяется наличие точки
   входа.
4. На первой директории `D` с точкой входа: если `T` — это `D/index` или `D/index.<ext>`, нарушения
   нет (это и есть вход через баррель). Иначе — нарушение с границей `D`.
5. Если ни на одном сегменте точки входа не нашлось — нарушения нет.

Директории, внутри которых уже находится `F` (уровень `M` и выше), не проверяются: модуль не закрыт
от самого себя. Вложенные точки входа не считаются: **верхняя граница выигрывает у ближней** — то,
как устроен модуль изнутри, снаружи не видно.

### Примеры

| ситуация                                              | результат                                        |
| ----------------------------------------------------- | ------------------------------------------------ |
| `F` и `T` в одной директории                          | разрешено                                        |
| `T` выше `F` по дереву                                | разрешено                                        |
| `T` внутри соседней директории с `index`              | нарушение, граница — эта директория              |
| `T` — сам `index` первой границы на пути              | разрешено                                        |
| `T` — `index.<ext>` первой границы (явное расширение) | разрешено                                        |
| `T` — `index` директории глубже первой границы        | нарушение, граница — первая директория с `index` |
| на пути нет ни одной точки входа                      | разрешено                                        |
| у `dirname(F)` и `dirname(T)` разные корни            | разрешено                                        |

```js
// feature/index.ts
// feature/internal/thing.ts

// other/file.ts — invalid
import { thing } from '../feature/internal/thing.js';
//                     ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
// Import bypasses the module barrel. Use '../feature' instead of '../feature/internal/thing.js'.

// other/file.ts — valid
import { thing } from '../feature';
```

### Точки входа

Точкой входа считается файл `index` с одним из расширений: `ts`, `tsx`, `js`, `jsx`, `mts`, `cts`,
`mjs`, `cjs`. Другие соглашения (например `rsc.ts`) правилом не распознаются — их можно исключить из
проверки через `files`/`ignores` в flat-конфиге.

## `settings.weld`

Правило понимает алиасы импортов, если они описаны в `settings.weld` — формат записи алиасов
совпадает с `paths` из `tsconfig.json`:

```js
// eslint.config.js
export default [
    {
        settings: {
            weld: {
                baseUrl: 'packages/app', // необязательно, по умолчанию '.'
                aliases: { '@src/*': ['src/*'] },
            },
        },
    },
];
```

`baseUrl` резолвится от `context.cwd` — текущей директории, из которой запущен ESLint. **Это отличие
от tsconfig**, где база отсчитывается от расположения файла конфига: в монорепе результат зависит от
того, откуда именно запущен линт.

### Нормализация записей

Каждая запись `{ключ: [якоря]}` превращается в одну или несколько пар `{prefix, anchor}`. Обе
стороны записи обрабатываются независимо — звёздочность ключа и якоря не обязана совпадать:

| запись                                  | префикс | якорь                     | почему                                                          |
| --------------------------------------- | ------- | ------------------------- | --------------------------------------------------------------- |
| `'@src/*': ['src/*']`                   | `@src`  | `<base>/src`              | снят хвост `/*` с обеих сторон                                  |
| `'@pkg': ['packages/pkg/src/index.ts']` | `@pkg`  | `<base>/packages/pkg/src` | базовое имя `index` + известное расширение → берётся директория |
| `'@cfg': ['src/config.ts']`             | `@cfg`  | —                         | обычный файл директорией не выражается, запись отбрасывается    |
| `'@dir': ['src/dir']`                   | `@dir`  | `<base>/src/dir`          | как есть                                                        |

Записи `'*': [...]` отбрасываются принудительно (пустой префикс совпал бы с любым именем пакета), а
формы со звёздочкой в середине (`'@a/*/b'`, `'src/*.ts'`) — потому что подстановкой префикса не
выражаются.

При разборе импорта выигрывает самый длинный подходящий префикс; при равных длинах — первая запись в
порядке объявления. При формировании исправленного пути выбирается запись с самым длинным якорем,
покрывающим найденную границу; если такой записи нет — правило откатывается на относительный путь.

### Три отхода от формата tsconfig

- **Беззвёздочные записи трактуются как префиксные.** В tsconfig `'@pkg'` без `*` означает точное
  совпадение специфаера. Здесь `@pkg/internal/thing` подпадает под запись `'@pkg'` так же, как под
  `'@pkg/*'` — это ровно тот обход границы, который правило должно ловить.
- **Значение-строка принимается вместо массива.** `{ '@pkg': 'src/pkg' }` — валидная запись, хотя
  tsconfig требует массив. Частая опечатка от руки с однозначным смыслом.
- **`baseUrl` отсчитывается от `context.cwd`**, а не от расположения файла конфига — см. выше.

## Опция `fix`

```js
rules: {
    'weld/no-barrel-bypass': ['error', { fix: true }],
}
```

По умолчанию `fix: false`: исправленный путь предлагается через ESLint suggestion (`--fix` его не
применяет), а не автоматически. Причина: правило не читает содержимое барреля и не знает,
реэкспортирует ли он нужное имя — `--fix` в теории может подставить путь, который ничего не
экспортирует, и сломать сборку. Включайте `fix: true` осознанно.

Кавычки в правке берутся из исходного литерала — правило не навязывает свой стиль кавычек.

## Поведение при неверных `settings.weld`

Если `settings.weld` задан, но не проходит валидацию (например, `aliases` — не объект), правило
**бросает исключение внутри `create()`**. Это значит, что ESLint сообщит об ошибке на каждом
проверяемом файле — намеренно: молча отключившееся из-за опечатки в конфиге правило хуже явно
упавшего.

## Что не проверяется

Сознательно вне области действия правила:

- `export … from` — реэкспорт не проверяется вовсе;
- содержимое барреля и цепочки реэкспорта — правило не читает файлы, только проверяет наличие точки
  входа на диске;
- дополнительные соглашения о точках входа (`rsc.ts` и подобные) — используйте `files`/`ignores`;
- SFC-баррели (`index.vue`, `index.svelte`) — набор расширений фиксирован восемью JS/TS-вариантами;
- импорты не-JS ресурсов (`.css`, `.svg`, `.json`, …) и специфаеры с `?`/`!` (`./x.svg?url`,
  `!!raw-loader!./x`) — баррель не может реэкспортировать такие ресурсы, поэтому предложенная правка
  была бы невыполнимой;
- существование цели импорта — этим занимается `import/no-unresolved`, а не это правило.
