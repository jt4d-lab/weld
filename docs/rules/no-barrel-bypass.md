# `weld/no-barrel-bypass`

Запрещает импорты, которые входят внутрь модуля мимо его точки входа (баррель).

## Что ловит правило

Единственный источник знания о границах модуля в этом правиле — расположение файлов `index.<ext>`
(`ts`, `tsx`, `js`, `jsx`, `mts`, `cts`, `mjs`, `cjs`, константа `ENTRY_EXTENSIONS`). Директория, в
которой лежит такой файл, объявляет себя модулем с публичным API: всё остальное в ней — внутреннее
дело модуля, и импортировать это извне напрямую нельзя, только через `index`.

Правило проектно-нейтральное: никакой отдельной конфигурации границ не требуется — граница
появляется в тот момент, когда в директории появляется `index.<ext>`, и исчезает, если его убрать.

Проверяются:

- `import ... from '...'` (включая `import type ... from '...'`);
- `import('...')` с строковым литералом аргумента;
- `require('...')` с строковым литералом аргумента (проверка синтаксическая — затенение
  идентификатора `require` не отслеживается).

Сообщение об ошибке указывается на строковом литерале пути.

## Алгоритм `findBarrier`

Все пути внутри правила — виртуальные, абсолютные от корня репозитория (`/src/feature/x.ts`), не от
диска. Обозначения:

- `F` — файл, откуда идёт импорт;
- `T` — путь цели импорта (уже разрешённый: относительный или через алиас);
- `M` — самая глубокая директория, общая для `dirname(F)` и `dirname(T)`;
- `D` — найденная граница.

Шаги:

1. `M` = общий префикс сегментов `dirname(F)` и `dirname(T)` (минимум — виртуальный корень `/`).
2. Взять сегменты `relative(M, T)`; последний сегмент (имя файла) в обходе директорий не участвует.
3. Идти по сегментам-директориям сверху вниз от `M` к `T`, накапливая текущий путь `D`, и на каждом
   шаге проверять, есть ли в `D` точка входа (`hasEntryPoint`).
4. На первой найденной `D` с точкой входа: если `T` — это `D/index` или `D/index.<ext>` (явное
   расширение), нарушения нет; иначе — нарушение с границей `D`.
5. Если сегменты кончились и точка входа не найдена — нарушения нет.

Границы на уровне `M` и выше не проверяются: модуль не закрыт от самого себя (импорт внутри одной
директории или «наверх» по дереву всегда разрешён). Отдельной проверки `F === T` нет — при
совпадающих директориях шаг 5 сразу даёт «нарушения нет».

Таблица свойств:

| ситуация                                                     | результат                       |
| ------------------------------------------------------------ | ------------------------------- |
| `F` и `T` в одной директории                                 | разрешено                       |
| `T` выше `F` по дереву                                       | разрешено                       |
| `T` внутри соседней директории с `index`                     | нарушение, `D` = эта директория |
| `T` — сам `index` первой границы на пути                     | разрешено                       |
| `T` — `index.<ext>` первой границы (явное расширение)        | разрешено                       |
| `T` — `index` директории глубже первой границы               | нарушение, `D` = первая граница |
| на пути нет ни одной точки входа                             | разрешено                       |
| вложенные границы: точки входа у `b` и `c`, цель `b/c/index` | нарушение, `D` = `b`            |

Вложенные `index` — деталь внутреннего устройства модуля: побеждает верхняя граница, а не ближняя к
цели.

Импорт между пакетами монорепы (например, из `/packages/a/src/x.ts` в
`/packages/b/src/internal/y.ts`) обрабатывается тем же алгоритмом без специального случая:
виртуальные пути делают такие импорты обычным пересечением границы.

## Примеры

Дано дерево:

```
src/
  feature/
    index.ts
    internal.ts
  consumer.ts
```

Valid:

```ts
// src/feature/internal.ts — импорт внутри своего же модуля
import { helper } from './other-file';

// src/consumer.ts — импорт через точку входа
import { thing } from './feature';

// голый пакет и @scope/pkg node_modules не резолвится вовсе
import { z } from 'zod';
```

Invalid:

```ts
// src/consumer.ts
import { helper } from './feature/internal';
// Import bypasses the module barrel. Use './feature' instead of './feature/internal'.
```

С алиасом `'@/*': ['src/*']`:

```ts
import { helper } from '@/feature/internal';
// Import bypasses the module barrel. Use '@/feature' instead of '@/feature/internal'.
```

## Формирование исправленного пути

Форма записи исходного специфайера сохраняется:

1. относительный импорт → относительный путь от `dirname(F)` до `D`, с префиксом `./`, если
   результат не начинается уже с `./` или `../` (директории вроде `.storybook` из-за ведущей точки
   не становятся относительным специфайером сами по себе);
2. если якорь алиаса исходного импорта покрывает `D` — используется тот же алиас;
3. если не покрывает — берётся алиас с самым длинным якорем среди тех, что покрывают `D`;
4. если ни один алиас не покрывает `D` — откат на относительный путь.

Расширение — часть той же формы. Если в исходном специфайере расширение записано явно, к пути
дописывается `/index.<то же расширение>`; если нет — предлагается голая директория `D`:

| исходный импорт         | предложение          |
| ----------------------- | -------------------- |
| `./feature/internal`    | `./feature`          |
| `./feature/internal.js` | `./feature/index.js` |
| `@/feature/internal.ts` | `@/feature/index.ts` |

Иначе правило ломало бы проекты, где расширения обязательны: в Node-ESM импорт директории не
резолвится вовсе, и предложенный `./feature` был бы заведомо нерабочим путём. Расширение берётся из
исходного импорта, а не с диска, — это факт про форму записи: в TypeScript под Node-ESM на диске
лежит `index.ts`, а в специфайере полагается писать `index.js`.

За вычетом этого хвоста `D` — всегда директория: расширение самого файла-цели в предложенный путь не
попадает.

## Настройки: `settings.weld`

```js
export default [
    {
        settings: {
            weld: {
                root: '.', // необязательно; по умолчанию — авто-поиск
                baseUrl: 'packages/app', // необязательно; по умолчанию '.'
                aliases: { '@/*': ['src/*'] },
            },
        },
    },
];
```

### `root`

Определяет корень репозитория, от которого строятся виртуальные пути.

- Если задан — берётся как есть; **относительное значение резолвится от `context.cwd`** (запуска
  ESLint), а не от расположения конфигурационного файла. Значение, не являющееся строкой, — ошибка.
- Если не задан — выполняется автопоиск: подъём от `context.cwd` вверх, ищется **самый верхний**
  `package.json` (обычно принадлежащий корню монорепы), а подъём останавливается на первой
  директории с `.git` (включительно — её `package.json` ещё учитывается) либо на корне файловой
  системы, если `.git` не встретился.
- Если автопоиск ничего не нашёл (нет ни одного `package.json` по пути наверх) — root молча
  становится самим `context.cwd`: отсутствие `package.json` — законная ситуация, ошибки нет.

Результат автопоиска кэшируется по `cwd` без TTL (в рамках жизни процесса ESLint смена корня
репозитория не ожидается).

### `baseUrl`

В отличие от `tsconfig`, где `baseUrl` отсчитывается от расположения самого `tsconfig.json`, здесь
**`baseUrl` отсчитывается от корня репозитория (`root`)**, а не от `context.cwd` и не от файла
конфигурации ESLint. Это осознанное отклонение: при авто-найденном `root` результат линтинга не
должен зависеть от того, из какой директории запущен ESLint. По умолчанию — `'.'` (сам `root`).
Значение, не являющееся строкой, — ошибка (как и у `root`).

### `aliases`

Формат записи совпадает с `paths` из `tsconfig.json` — объект «префикс → один или несколько путей»,
но со следующими отличиями от tsconfig-конвенции:

- значение записи может быть **строкой**, не только массивом (частая опечатка с однозначным смыслом
  — принимается намеренно);
- специфайер подходит под запись, если равен префиксу целиком **или** начинается с `prefix + '/'` —
  **включая записи без `*`**. Это отход от tsconfig, где беззвёздочная запись матчится только на
  точное совпадение: например, `@pkg` (без `/*`) в этом правиле разрешает и `@pkg/internal/thing` —
  ровно тот способ обойти баррель, который правило должно ловить.

Нормализация каждой записи (обе стороны — ключ и значение — обрабатываются независимо):

| запись                                  | префикс | якорь                     | почему                                                         |
| --------------------------------------- | ------- | ------------------------- | -------------------------------------------------------------- |
| `'@/*': ['src/*']`                      | `@src`  | `<base>/src`              | хвост `/*` снят с обеих сторон                                 |
| `'@pkg': ['packages/pkg/src/index.ts']` | `@pkg`  | `<base>/packages/pkg/src` | базовое имя `index` с известным расширением → взята директория |
| `'@cfg': ['src/config.ts']`             | `@cfg`  | — (запись отбрасывается)  | обычный файл директорией не выражается                         |
| `'@dir': ['src/dir']`                   | `@dir`  | `<base>/src/dir`          | как есть, без изменений                                        |

где `<base>` — виртуальный путь `resolvePath('/', baseUrl ?? '.')`.

Прочие правила разбора:

- значения-массивы разворачиваются в отдельные записи `{ prefix, anchor }`; дубликаты
  `prefix + anchor` схлопываются;
- при разборе импорта выигрывает самый длинный подходящий префикс; при равных длинах — та запись,
  что объявлена раньше;
- при построении исправленного пути выигрывает запись с самым длинным якорем, покрывающим найденную
  границу;
- принимаются только ключи и якоря без `*` либо с хвостом `/*`; звёздочка в середине записи — запись
  отбрасывается; запись `'*'` отбрасывается принудительно (пустой префикс сломал бы отсев голых
  пакетов из `node_modules`);
- ошибки валидации: `aliases` — не объект, значение записи — не строка и не массив, элемент массива
  — не строка. Во всех случаях бросается исключение с текстом, называющим конкретный ключ и место
  значения в конфиге (`settings.weld.aliases['@bad']`).

Разбор алиасов кэшируется по объекту `settings.weld.aliases` — повторный разбор одного и того же
конфига переиспользует результат. В запись кэша входит и `baseUrl`: один и тот же объект алиасов при
другом `baseUrl` даёт другие якоря и разбирается заново.

## Опции правила

```js
{
    rules: {
        'weld/no-barrel-bypass': ['error', { fix: false }],
    },
}
```

Схема опций — один объект (лишние ключи запрещены):

| опция     | тип       | по умолчанию                     |
| --------- | --------- | -------------------------------- |
| `fix`     | `boolean` | `true`                           |
| `root`    | `string`  | значение `settings.weld.root`    |
| `baseUrl` | `string`  | значение `settings.weld.baseUrl` |
| `aliases` | `object`  | значение `settings.weld.aliases` |

### `root`, `baseUrl`, `aliases` в опциях

Это те же самые настройки, что и в `settings.weld` (формат, значения по умолчанию и правила разбора
— из раздела «Настройки: `settings.weld`» выше), но заданные на самом правиле. Заданная опция
целиком заменяет одноимённое поле секции; незаданная — не влияет ни на что, читается
`settings.weld`.

Зачем: `settings` в flat config задаются на конфигурационный объект целиком и общие для всех правил,
а опции — на конкретное правило в конкретном блоке `files`. Это способ пролинтовать часть монорепы с
другим `root` или другим набором алиасов, не заводя отдельную секцию `settings` (и не сбивая её
остальным правилам):

```js
export default [
    {
        settings: { weld: { root: '.', aliases: { '@/*': ['src/*'] } } },
        rules: { 'weld/no-barrel-bypass': 'error' },
    },
    {
        files: ['legacy/**'],
        rules: {
            'weld/no-barrel-bypass': [
                'error',
                { root: './legacy', baseUrl: 'src', aliases: { '@legacy/*': ['app/*'] } },
            ],
        },
    },
];
```

`baseUrl` действует и на алиасы из `settings.weld`: якоря считаются от того `baseUrl`, который
победил, — переопределить одни только алиасы, оставив им чужой `baseUrl`, было бы ловушкой.

Значения опций проверяются тем же слоем, что и `settings.weld` (типы полей — ещё и схемой ESLint); в
тексте ошибки источник называется как `options.<имя>` вместо `settings.weld.<имя>`.

### `fix`

Правило всегда объявляет `meta.fixable: 'code'` и `meta.hasSuggestions: true`; опция `fix` решает,
куда уходит одна и та же правка:

- `fix: true` (по умолчанию) — правка применяется автофиксом (`eslint --fix`);
- `fix: false` — та же правка доступна только как suggestion (`messageId: 'useBarrel'`),
  автоматически не применяется.

**Автофикс включён по умолчанию сознательно**: замена специфайера — механическая правка формы пути,
она не читает содержимое барреля и не проверяет, реэкспортирует ли он нужное имя, но всегда
синтаксически корректна. Если нужна ручная проверка перед применением (например, из-за отдельного
правила про содержимое реэкспортов, см. «Что правило не проверяет»), автофикс можно выключить через
`fix: false`.

Кавычки в замене берутся из исходного литерала (`source.raw[0]`), чтобы не конфликтовать с prettier.

`configs.recommended` и `configs.strict` включают правило одинаково — как `'error'` без опций (то
есть с автофиксом по умолчанию).

## Поведение в крайних случаях

- **Некорректный `settings.weld`** (например, `root` или `baseUrl` не строка, `aliases` — не объект,
  значение алиаса не строка/массив) — правило бросает исключение внутри `create()`. ESLint репортует
  ошибку правила **на каждом проверяемом файле**. Это намеренно: молча отключившееся из-за опечатки
  в конфиге правило хуже громко упавшего. Значения, приходящие вместо настроек из опций правила,
  проверяются теми же правилами; в тексте ошибки источник называется как `options.<имя>`.
- **Файл вне `root`** (например, `context.filename` указывает за пределы найденного/заданного корня
  репозитория, либо `filename` не абсолютный — как `<input>` при `Linter#verify` без пути) — правило
  молча ничего не проверяет (`toVirtual` возвращает `null`, `create()` возвращает пустой объект
  обработчиков). Ошибки при этом не возникает.

## Что правило сознательно не проверяет

- `export ... from '...'` — реэкспорты не анализируются;
- содержимое барреля и цепочки реэкспортов — правило не проверяет, что импортируемое имя реально
  доступно через `index`, оно лишь предлагает синтаксически корректный путь к баррелю;
- дополнительные точки входа и SFC-баррели (например, `index.vue`) — набор `ENTRY_EXTENSIONS`
  фиксирован;
- импорты не-JS ресурсов (`.css`, `.svg`, `.json`, `.png` и т. п.) и специфайеры с `?`/`!`
  (`./x.svg?url`, `!!raw-loader!./x`) — это инструкции сборщику, а не пути, которые можно переписать
  на баррель;
- голые импорты пакетов и `@scope/pkg` — `node_modules` не резолвится вовсе;
- абсолютные специфайеры (`/foo`) — для них не определена форма вывода исправленного пути;
- чтение алиасов из `tsconfig.json` (auto-discovery) — алиасы задаются только через
  `settings.weld.aliases`;
- эвристики поиска `root`, отличные от «самый верхний `package.json` в границах `.git`».
