# `weld/no-barrel-bypass`

Директория, в которой есть файл `index.<ext>`, объявляет себя модулем с публичным API. Правило ловит
импорты, входящие внутрь такой директории мимо её точки входа, и предлагает исправленный путь —
через её баррель (`index`), а не напрямую к внутреннему файлу.

Правило проектно-нейтральное: оно ничего не знает ни про слои WELD, ни про имена директорий.
Единственный источник знания о границах модулей — расположение файлов `index` на диске.

## Что ловит

Правило проверяет три вида узлов:

- `import ... from '...'` (включая `import type`);
- `import('...')` с импортируемой строкой (динамический импорт с нелитеральным аргументом не
  проверяется — там нет строки, от которой можно оттолкнуться);
- `require('...')` — распознаётся синтаксически, по имени вызываемой функции; переприсваивание или
  затенение локальной переменной `require` не отслеживается.

Сообщение об ошибке вешается на литерал пути импорта.

`export ... from '...'` **не проверяется** — сознательно, см.
[«Что вне области действия»](#что-вне-области-действия).

## Алгоритм

Ядро правила — три чистые функции без обращения к диску за целью импорта (существование цели — дело
`import/no-unresolved`, не этого правила):

```
specifier ──parseSpecifier──▶ Target {path, form}
                                 │
                    findBarrier(fromDir, path, hasEntryPoint) ──▶ D | null
                                 │
                    renderSpecifier(form, fromDir, D, aliases) ──▶ исправленный путь
```

- `parseSpecifier` разбирает строку импорта в абсолютный путь цели и форму записи (относительная или
  через алиас). Строка импорта сама и есть путь: относительная резолвится от директории файла,
  алиасная — подстановкой якоря.
- `findBarrier` идёт от общей директории файла и цели вниз к цели и ищет первую директорию с точкой
  входа, которую импорт пробивает.
- `renderSpecifier` превращает найденную границу обратно в специфаер — **в той же форме**, в которой
  был написан исходный импорт (относительный импорт остаётся относительным, алиасный — алиасным).

Единственная точка обращения к диску — предикат `hasEntryPoint(dir)`, инжектируемый снаружи (в
рантайме — реализация с TTL-кэшем 30 секунд, тот же порядок, что у `import/cache`).

### Таблица свойств `findBarrier`

Обозначения: `F` — файл с импортом, `T` — путь цели.

| ситуация                                              | результат                       |
| ----------------------------------------------------- | ------------------------------- |
| `F` и `T` в одной директории                          | разрешено                       |
| `T` выше `F` по дереву                                | разрешено                       |
| `T` внутри соседней директории с `index`              | нарушение, `D` = эта директория |
| `T` — сам `index` первой границы на пути              | разрешено                       |
| `T` — `index.<ext>` первой границы (явное расширение) | разрешено                       |
| `T` — `index` директории глубже первой границы        | нарушение, `D` = первая граница |
| на пути нет ни одной точки входа                      | разрешено                       |
| у `dirname(F)` и `dirname(T)` разные корни            | разрешено                       |

Ключевое следствие: **верхняя граница выигрывает у ближней**. Если импорт пробивает сразу несколько
вложенных модулей, репортится самая внешняя из них — устройство модуля изнутри (какие поддиректории
у него свои `index`) снаружи не видно и не важно.

Границы, внутри которых уже находится `F` (файл с импортом), не проверяются — модуль не закрыт от
самого себя. Импорт `index` собственной или родительской директории всегда разрешён.

Точками входа считаются файлы `index.ts`, `index.tsx`, `index.js`, `index.jsx`, `index.mts`,
`index.cts`, `index.mjs`, `index.cjs`.

## Примеры

Дано: `src/feature/index.ts` (баррель) и `src/feature/internal/thing.ts` (внутренний файл).

Неверно (нарушение — прямой импорт внутреннего файла в обход барреля):

```ts
// src/other/file.ts
import { thing } from '../feature/internal/thing';
```

Правило предложит исправление:

```ts
import { thing } from '../feature';
```

Верно (импорт через баррель):

```ts
import { thing } from '../feature';
```

Верно (импорт соседа без границ на пути — между `file.ts` и `sibling/thing.ts` нет `index`):

```ts
// src/feature/file.ts
import { x } from '../sibling/thing';
```

Верно (импорт файла внутри собственного модуля — файл уже находится внутри границы):

```ts
// src/feature/internal/other.ts
import { thing } from './thing';
```

## `settings.weld`

Алиасы (пути вроде `@src/*`) настраиваются через `settings.weld` в конфиге ESLint, формат близок к
`paths` из `tsconfig.json`:

```js
export default [
    {
        settings: {
            weld: {
                baseUrl: 'packages/app', // необязательно, по умолчанию '.'
                aliases: { '@src/*': ['src/*'] },
            },
        },
        rules: {
            'weld/no-barrel-bypass': 'error',
        },
    },
];
```

`<base>` = `baseUrl`, разрешённый относительно `context.cwd` (текущей рабочей директории, из которой
запущен ESLint).

### Нормализация записи

Каждая запись `aliases` независимо нормализуется в пару `{ prefix, anchor }`. Звёздочность ключа и
значения не обязана совпадать — каждая сторона обрабатывается сама по себе:

| запись                                  | префикс | якорь                     | почему                                                        |
| --------------------------------------- | ------- | ------------------------- | ------------------------------------------------------------- |
| `'@src/*': ['src/*']`                   | `@src`  | `<base>/src`              | снят хвост `/*` с обеих сторон                                |
| `'@pkg': ['packages/pkg/src/index.ts']` | `@pkg`  | `<base>/packages/pkg/src` | базовое имя `index` + известное расширение → берём директорию |
| `'@cfg': ['src/config.ts']`             | `@cfg`  | —                         | обычный файл директорией не выражается, запись отбрасывается  |
| `'@dir': ['src/dir']`                   | `@dir`  | `<base>/src/dir`          | как есть                                                      |

Принимаются только ключи и якоря либо без `*`, либо оканчивающиеся ровно на `/*`. Записи со
звёздочкой в середине (`'@a/*/b'`, `'src/*.ts'`) молча отбрасываются — подстановкой префикса они не
выражаются. Запись `'*': [...]` отбрасывается принудительно: пустой префикс совпал бы с чем угодно,
включая имена пакетов из `node_modules`.

Массив якорей разворачивается в отдельные записи `{ prefix, anchor }`, дубликаты по паре
`prefix + anchor` схлопываются. При разборе строки импорта выигрывает самый длинный подходящий
префикс; при равных префиксах — первая запись в порядке объявления. При рендере исправленного пути
выигрывает запись с самым длинным якорем, покрывающим найденную границу.

### Три отхода от формата `tsconfig`

1. **Беззвёздочные записи трактуются как префиксные.** В `tsconfig` запись `'@pkg'` (без `*`)
   означает точное совпадение специфаера с ключом. Здесь `'@pkg'` подходит и под `@pkg`, и под
   `@pkg/internal/thing` — потому что именно такой импорт (уход вглубь пакета мимо его барреля) и
   должно ловить правило. Если трактовать `'@pkg'` буквально как точное совпадение, обход границы
   через беззвёздочный алиас остался бы незамеченным.
2. **Значение-строка принимается вместо массива.** В `tsconfig.json` значение `paths[key]` всегда
   массив; здесь `{ '@src': 'src' }` (строка вместо `['src']`) тоже валиден — это частая опечатка от
   руки с однозначным смыслом, отклонять её нет причин.
3. **`baseUrl` резолвится от `context.cwd`, а не от расположения конфига.** В `tsconfig.json` база
   отсчитывается от директории самого файла `tsconfig.json`. Здесь — от текущей рабочей директории
   ESLint (`context.cwd`). В монорепе результат зависит от того, из какой директории запущен
   `eslint`, а не от того, где лежит конфиг.

### Ошибки в `settings.weld`

Если `settings.weld` или `settings.weld.aliases` не проходят валидацию (не объект, значение не
строка и не массив, элемент массива не строка), правило **бросает исключение** — а не молча
выключается или игнорирует некорректную запись. ESLint в этом случае сообщит об ошибке правила на
каждом проверяемом файле, а не только там, где встретился нарушающий импорт.

Это осознанное решение: молча отключившееся из-за опечатки правило хуже громко упавшего — с
неверными `settings.weld` легко не заметить, что защита от обхода барреля просто не работает.

Записи, отброшенные по таблице нормализации выше (`'*'`, звёздочка в середине, обычный файл без
`index`), не считаются ошибкой — это валидный `paths`, просто невыразимый директорией, поэтому такие
записи молча пропускаются.

## Опция `fix`

```js
rules: {
    'weld/no-barrel-bypass': ['error', { fix: false }],
}
```

По умолчанию `fix: true`. Правило всегда умеет предложить исправление и по умолчанию отдаёт его как
автофикс, применяемый обычным `eslint --fix`, а не только как **suggestion** (правку из меню
редактора или `--fix-type suggestion`).

Оговорка: правило не читает содержимое барреля и не разворачивает его реэкспорты — оно не знает,
реэкспортирует ли `index` то самое имя, которое импортировалось напрямую. Автофикс, применённый
массово по всему проекту, в теории способен подставить путь через баррель, который на самом деле не
реэкспортирует нужное имя, и тем самым сломать сборку. Если это неприемлемо, выключите автофикс
опцией `fix: false` — тогда правка останется suggestion, применяемым вручную и по одному месту за
раз.

Кавычки в правке берутся из исходного литерала импорта (`'` или `"`), поэтому автофикс не переводит
файл на свой стиль кавычек и не конфликтует с prettier.

## Что вне области действия

Правило сознательно не проверяет и не умеет:

- **`export ... from '...'`** — реэкспорт из чужого модуля не отслеживается вовсе. Это отдельная
  задача («баррель реэкспортирует только на один уровень»), которой пока нет.
- **Содержимое барреля и цепочки реэкспорта** — правило не читает, что именно `index.ts`
  реэкспортирует; оно только проверяет факт наличия файла `index.<ext>` в директории.
- **Дополнительные точки входа** (соглашения вида `rsc.ts`, `public-api.ts`) — распознаётся только
  `index.<ext>`. Такие соглашения гасятся через `files`/`ignores` в самом flat-конфиге, а не
  настройками правила.
- **SFC-баррели** (`index.vue`, `index.svelte`) — список расширений точки входа фиксирован восемью
  JS/TS-расширениями и не включает форматы single-file components.
- **Импорты не-JS ресурсов и специфаеры с `?`/`!`** — `parseSpecifier` возвращает `null` для голого
  имени пакета, `@scope/pkg`, абсолютного специфаера (`/foo`), специфаеров с `?` или `!`
  (`./x.svg?url`, `!!raw-loader!./x`) и для целей с расширением вне списка точек входа (`.css`,
  `.svg`, `.json`, `.png` и т. п.). Последнее — сознательное сужение: баррель `index.ts` не может
  реэкспортировать CSS, поэтому предложенная правка для `./feature/internal/styles.css` была бы
  невыполнимой, а с включённым `fix` — ломающей сборку.
