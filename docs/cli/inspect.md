# `weld inspect <file>`

Выводит информацию о файле: путь, путь импорта и положение в схеме слоев.

## Результат

```
$ weld inspect src/modules/billing/features/panel.ts
file:      src/modules/billing/features/panel.ts
alias:     @/modules/billing/features/panel.ts
module:    billing
layer:     features
innerPath: panel.ts
```

### `file`

путь к файлу от корня репозитория: корень зависит от места запуска, а вывод — нет.

### `alias`

специфаер, которым этот файл импортируется по алиасу. Форму выбирает запись алиаса, поэтому правил
несколько.

### `module`

имя модуля файла: `@root`, если файл не попал ни в один модуль — где угодно внутри `srcDir`, включая
`src/utils/...` и `src/modules/x.ts`, — иначе имена модулей в контейнерах от внешнего к внутреннему,
соединенные `::`: `billing::subscription` для `src/modules/billing/modules/subscription/...`. Само
имя хранится цепочкой, `::` — только форма вывода.

### `layer`

имя слоя, в который попадает файл, либо `@unknown`. Слой определяется первым сегментом директории от
корня проекта или модуля и глубже не ищется: `src/modules/billing/features/widgets/panel.ts` лежит в
слое `features`, а не `widgets`.

Файл, лежащий прямо в корне проекта или модуля, слоя не имеет и печатается как `@unknown`. Этот же
`@unknown` обозначает ветку ниже всех слоев модуля и код, не относящийся ни к одному слою проекта, —
даже если метки `@unknown` в схеме нет.

### `innerPath`

путь от корня слоя. У `@unknown` корнем становится корень модуля, а у `@root` — `srcDir`. На месте
имени модуля или слоя корнем остается содержащий их контейнер, поэтому сам файл попадает в путь.

Примеры при `srcDir: 'src'`, `modulesDir: 'modules'`, слое проекта `app` и слое модуля `features`:

| Файл                                                         | `module`                | `layer`    | `innerPath`         |
| ------------------------------------------------------------ | ----------------------- | ---------- | ------------------- |
| `src/app/nested/pages/x.ts`                                  | `@root`                 | `app`      | `nested/pages/x.ts` |
| `src/utils/format.ts`                                        | `@root`                 | `@unknown` | `utils/format.ts`   |
| `src/modules/billing/features/panel.ts`                      | `billing`               | `features` | `panel.ts`          |
| `src/modules/billing/modules/subscription/features/panel.ts` | `billing::subscription` | `features` | `panel.ts`          |
| `src/modules/billing/api/x.ts`                               | `billing`               | `@unknown` | `api/x.ts`          |
| `src/modules/billing/modules/foo.ts`                         | `billing`               | `@unknown` | `modules/foo.ts`    |
| `src/modules/x.ts`                                           | `@root`                 | `@unknown` | `modules/x.ts`      |

## Форма специфаера

- Файл точки входа схлопывается в директорию: `src/feature/index.ts` печатается как `@/feature`.
  Если у ключа алиаса есть собственный хвост (`@/feature/* → src/feature/*`), голый `@/feature`
  такой записью не резолвится, поэтому печатается `@/feature/index.ts`.
- Точный ключ без хвоста (`@/config → src/config`) уже сам является специфаером:
  `src/config/index.ts` печатается как `@/config`, и имя файла к нему не дописывается —
  `@/config/index.ts` такой записью не резолвится.
- Точный ключ не выражает путь ниже своего якоря (`@/config/other.ts` при якоре `src/config`
  TypeScript не находит), поэтому такой файл печатается специфаером более широкого звездного алиаса
  — `@/config/other.ts` при `@/* → src/*`; если звездного алиаса нет, печатается виртуальный путь,
  как и для непокрытого файла.
- Если файл лежит прямо в директории алиаса с хвостом в ключе, хвостом становится имя файла:
  `src/index.ts` при алиасе `@/* → src/*` печатается как `@/index.ts` — голый `@` таким импортом не
  резолвится.
- Если файл не покрывает ни один алиас, в `alias` печатается виртуальный путь от корня репозитория
  (`/src/feature/internal.ts`), а не относительный путь. `index.<ext>` в корне репозитория схлопнуть
  некуда: печатается `/index.ts`, а не `/`.

## Имена путей

Ни одно имя файла или директории внутри `srcDir` не может содержать `@` и `:`, точки разрешены: `@`
занят метками схемы, `:` — разделителем цепочки модулей. Ограничение проверяется при определении
метаданных, поэтому такой путь — ошибка команды, а не повод напечатать неоднозначное имя. Сегменты
самого `srcDir` к проверке не относятся.

Файл вне `srcDir` метаданных не имеет: `weld inspect` на нем завершается ошибкой. Схема с
`srcDir: '.'` применима ко всему репозиторию.

## Схема обязательна

`weld inspect` запрашивает схему слоев, поэтому `layers` и `moduleLayers` должны быть заданы и
корректны: без схемы или с ошибкой в ней команда завершается текстом ошибки и кодом 1 — в том числе
при `--json`, где в stdout печатается `{ "error": ... }`. Остальные потребители настроек схему не
читают, и кривая схема им не мешает.

Схема берется из эффективного конфига файла — оттуда же, откуда остальные настройки. Из опций правил
CLI читает опции первого правила `weld/*` с объектом опций, поэтому при разных схемах у разных
правил команда покажет схему этого правила. Если первое правило схему не задает, значение берется из
`settings.weld`; нет схемы и там — команда завершается ошибкой.

## JSON

При `--json` печатаются те же поля машинной формы: `file`, `alias`, `module`, `layer`, `innerPath`.
Отличие одно: отсутствие алиаса выражается `"alias": null`, а не виртуальным путем.

```json
{
    "file": "src/modules/billing/api/x.ts",
    "alias": null,
    "module": "billing",
    "layer": "@unknown",
    "innerPath": "api/x.ts"
}
```
