# `weld config <path>`

Выводит настройки, которые фактически применяются к файлу, включая разобранные алиасы и схему слоев.
Вывод — диагностический отчет: сломанная настройка не останавливает команду, а печатает своё
состояние; при собственной ошибке какой-либо настройки или секции код возврата — 1.

## Результат

```
$ weld config src/feature/internal.ts
file:   src/feature/internal.ts
config: eslint.config.js
settings.weld:
  repoRoot:       /home/user/project
  aliasesBaseUrl: .
  tsconfig:       tsconfig.json
  aliases:
    @/* → /src/*
  srcDir:         /src
  modulesDir:     modules
  layers:         app, @modules, @unknown
  moduleLayers:   features
```

### `file`

путь к файлу от корня репозитория. Для директории печатается сэмпл — файл, представляющий ее в
выводе, — с пометкой `(sample of <аргумент>)`; как он выбирается, описано ниже. Если эффективный
корень не получен — `repoRoot` в состоянии `invalid` или `unresolved` — печатается исходный
абсолютный путь: откоренить его нечем, и проверка «файл внутри корня» в этом случае не выполняется.

### `config`

примененный ESLint-конфиг, тоже от корня репозитория; тот же абсолютный fallback, что у `file`.
Конфиг вне корня (через `--config` или найденный выше `.git`) печатается абсолютным путем:
относительного пути от корня для него не существует. Когда конфигов в проекте несколько, эта строка
и есть ответ на вопрос, откуда взялись напечатанные настройки.

### `repoRoot`

действующий корень репозитория, а не значение из конфига: при автопоиске он поднимается до якорей
алиасов из tsconfig. Печатается абсолютным, потому что по нему разрешаются остальные пути. Пометок
происхождения значения нет: отличить `repoRoot` из конфига от найденного автоматически по выводу
нельзя.

### `aliasesBaseUrl`

значение из конфига или из опций правила; не задано ни там, ни там — `.`.

### `tsconfig`

значение из конфига или из опций правила; не задано ни там, ни там — `tsconfig.json`.

### `aliases`

разобранные алиасы. Запись печатается в форме `tsconfig`: `<prefix>/* → <anchor>/*`, а у точного
ключа хвоста `/*` нет ни с одной стороны (`@/config → /src/config`). Алиасов нет — печатается
`aliases: (none)`.

### `srcDir`

директория исходников проекта в схеме слоев — виртуальный путь от корня репозитория. Не задана —
`/src` по умолчанию.

### `modulesDir`

имя контейнера вложенных модулей. Не задано — `modules` по умолчанию.

### `layers`

слои проекта в схеме: разобранные значения в исходном порядке, через запятую. Список не задан —
`(not set)`: допустимое отсутствие, не ошибка.

### `moduleLayers`

слои модулей в схеме; те же правила, что у `layers`.

## Состояния настроек

Каждая настройка печатается в одном из четырех состояний:

- **значение** — настройка разобрана и печатается как есть;
- **`invalid`** — собственное значение невалидно: на месте значения печатается сообщение об ошибке.
  Сообщение называет источник значения — `settings.weld.<поле>` или `options.<поле>` — а для списков
  еще и индекс элемента;
- **`(unresolved: <зависимость>)`** — значение нельзя вычислить, потому что не разрешена названная
  зависимость. Собственной ошибки для такой настройки не придумывается: автоматические алиасы при
  сломанном корне получают `(unresolved: repoRoot)`, явные при невалидной базе —
  `(unresolved: aliasesBaseUrl)`, а настройки, которые не прочитать из невалидной секции, —
  `(unresolved: settings.weld)`;
- **`(not set)`** — допустимое отсутствие необязательного значения: `layers` или `moduleLayers` без
  схемы.

Невалидная секция `settings.weld` печатается один раз, сразу после имени секции:
`settings.weld: <сообщение>`. Настройки, которые из секции не читаются, получают состояние
`(unresolved: settings.weld)`, а собственные значения из опций правила проверяются независимо.

Каждая сломанная настройка держит собственную ошибку: каскад одинаковых сообщений по зависимым полям
не печатается, и вычислять значение спекулятивно — подставив фиктивную зависимость — команда не
пытается.

## Схема слоев

Команда разбирает схему небросающим диагностическим разбором: кривое поле получает собственное
сообщение, остальные поля и настройки печатаются как обычно. Проверки идут в порядке «сначала свой
формат, затем зависимости»: невалидное поле печатает собственную ошибку, даже если его зависимость
тоже сломана, а корректное поле, которое нельзя полностью проверить из-за зависимости, получает
`unresolved`. Совместные проверки двух списков выполняются только когда оба заданы: отсутствие
одного не превращает другой в ошибку.

Отсутствие списков не ошибка: `layers` и `moduleLayers` без схемы печатают `(not set)` и код
возврата не меняют.

Бросающее поведение сохраняется там, где схема обязательна: правила линтинга и `weld inspect`
запрашивают схему через бросающий путь, поэтому кривая схема для них — ошибка с кодом 1, а не
частичный отчет.

## Код возврата

0 — отчет напечатан, собственных ошибок нет. 1 — есть хотя бы одно состояние `invalid` или ошибка
секции `settings.weld`: отчет при этом печатается полностью, меняется только код возврата. Состояния
`unresolved` и `not set` сами по себе код не меняют.

Отдельный случай — ошибка самой команды: нет ESLint, нет годного файла в директории, либо файл вне
вычисленного корня. Отчет в этом случае не печатается; сообщение уходит в stderr с кодом 1 (в
`--json` — в stdout как `{"error": …}`).

## JSON-вывод

`--json` печатает тот же отчет машиночитаемо:

```json
{
    "file": "src/feature/internal.ts",
    "configFile": "eslint.config.js",
    "settings": {
        "repoRoot": "/home/user/project",
        "aliasesBaseUrl": ".",
        "tsconfig": "tsconfig.json",
        "aliases": [{ "prefix": "@", "anchor": "/src", "star": true }],
        "srcDir": "/src",
        "modulesDir": "modules",
        "layers": ["app", "@modules", "@unknown"],
        "moduleLayers": ["features"]
    },
    "problems": {}
}
```

Для директории добавляется `sampleOf` — аргумент, как у текстового `(sample of …)`.

- `settings` хранит простые значения; настройка в состоянии `invalid` или `unresolved` — `null`.
- `problems` — объект, ключ которого — имя настройки, или `settings.weld` для ошибки секции: для
  `invalid` значение — `{ "status": "invalid", "message": … }`, для `unresolved` —
  `{ "status": "unresolved", "dependency": … }`.
- `null` в `settings` без записи в `problems` — это состояние `not set`: необязательное значение
  отсутствует, ошибки нет.

Пример с невалидным корнем, зависящими от него алиасами и отсутствующими списками схемы:

```json
{
    "file": "/home/user/project/src/feature/internal.ts",
    "configFile": "/home/user/project/eslint.config.js",
    "settings": {
        "repoRoot": null,
        "aliasesBaseUrl": ".",
        "tsconfig": "tsconfig.json",
        "aliases": null,
        "srcDir": "/src",
        "modulesDir": "modules",
        "layers": null,
        "moduleLayers": null
    },
    "problems": {
        "repoRoot": {
            "status": "invalid",
            "message": "settings.weld.repoRoot must be a string, got number"
        },
        "aliases": {
            "status": "unresolved",
            "dependency": "repoRoot"
        }
    }
}
```

Код возврата тот же, что в текстовом режиме: 1 при собственной ошибке, иначе 0.

## Директория вместо файла

Сэмплом становится первый файл с модульным расширением, которому примененный конфиг задает настройки
WELD: игнорируемые файлы пропускаются, а файл, к которому конфиг ничего не добавляет (вне шаблонов
`files` и без глобального слоя), сэмплом не считается. Сверх того, файл без `settings.weld` и без
опций правил `weld/*` уступает любому файлу, которому они достаются: поэтому `jest.config.js` или
`next.config.mjs` из корня проекта сэмплом не станут, даже если сортируются раньше `src/`, —
глобальный слой конфига (`weld.configs.recommended`, общий `{ rules }`) делает непустым конфиг
любого линтуемого файла, но настроек WELD ему не передает. Если настроек WELD в конфиге нет вовсе,
сэмплом становится первый годный файл. Файл с именем `eslint.config.*` сэмплом не становится
никогда: он тоже линтуемый, но настроек директории не представляет.

Обход идет вглубь, а записи каждой директории перебираются по алфавиту; `node_modules` и скрытые
директории пропускаются. В директорию с собственным `eslint.config.*` обход не заходит: файлы там
описывает этот конфиг, а конфиг команды выбран по пути аргумента, так что пара `file:`/`config:`
описывала бы разные конфиги одного файла — прямой запрос `weld config <файл>` ответил бы другим
`config:` и другими настройками. Поэтому `weld config packages` в монорепе с пакетными конфигами
отвечает ошибкой `no lintable files in packages`: файлов под выбранным конфигом в этой директории
нет. С `--config` границы нет — указанный конфиг применяется к любому пути под текущей директорией.

Обход директории ограничен: 5000 записей — предел просмотра. Если годный файл к этому моменту
найден, команда возвращает его, а не ошибку: предел ограничивает работу, а не уже полученный ответ.
Ошибка `no lintable files … (stopped after 5000 entries)` появляется, только когда ответа нет.
