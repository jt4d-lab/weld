# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this
repository.

## Что это за репозиторий

WELD (Well-Encapsulated Layered Design) — подход к организации кода во frontend-приложениях плюс
инструменты для автоматической проверки его правил. Репозиторий должен содержать две связанные
части:

1. **Документацию подхода** — как раскладывать приложение по слоям и где проводить границы между
   модулями.
2. **ESLint-плагин** — проверку этих правил в CI/редакторе, потому что договорённостями в команде
   такие границы не удерживаются.

Ключевые идеи, задающие рамку для любых решений здесь:

- **Строгая инкапсуляция.** Модуль публикует наружу узкий, осознанно спроектированный интерфейс; всё
  остальное — его внутреннее дело.
- **Слои задают направление зависимостей**, инкапсуляция не даёт зависимостям расползтись в обход
  этого направления.

Правило плагина без соответствующего раздела в документации (и наоборот) — признак того, что две
части разошлись.

## Текущее состояние

Каркас пакета `eslint-plugin-weld` готов (сборка, тесты, CI, автопубликация); реализовано два
правила, оба зарегистрированы в `src/rules/index.ts`:

- `weld/no-barrel-bypass` (`src/rules/no-barrel-bypass/`) — граница модуля; включено в
  `configs.recommended`/`configs.strict`;
- `weld/no-illegal-layer-dependency` (`src/rules/no-illegal-layer-dependency/`) — направление
  зависимостей между слоями; тоже включено в `configs.recommended`/`configs.strict`. Схемы по
  умолчанию у плагина нет и быть не может (её знает только проект), а без схемы правило бросает
  исключение — поэтому **оба пресета требуют `settings.weld.layers`**. Цена решения принята
  осознанно: молча отключившееся правило хуже громко упавшего, но конфиг без схемы теперь неполон
  даже для тех, кому нужен только `no-barrel-bypass`.

У каждого есть страница в `docs/rules/`; общие для всех правил настройки — в `docs/settings.md`:
внутри страницы одного правила они не живут (см. «Добавление правила» ниже).

Формат схемы слоёв зафиксирован вместе с правилом направления: `layers`, `moduleLayers` и
`moduleDir` в `settings.weld` (разбор — `src/settings/layers.ts`, описание — `docs/settings.md`).

Документация подхода: четыре идеи (публичный API директории, однонаправленность зависимостей, слои
задаёт проект, общие слои и фрактальность модулей) тезисно записаны сразу в нескольких местах —
`docs/index.md` (блок `features` home-страницы, сокращённый набор), `docs/core-concepts/index.md`
(все четыре, с переходами на статьи), `docs/get-started/overview.md` и `README.md`. Правка идеи —
правка всех этих мест. Развёрнутая статья есть у трёх из четырёх:
`docs/core-concepts/public-api.md`, `direction.md` (её и проверяет `no-illegal-layer-dependency`) и
`layers.md`; у четвёртой («общие слои и фрактальность модулей») статьи ещё нет — переход на неё с
`docs/core-concepts/index.md` не ставится, пока её не написали.

Есть слой `src/host/` — граница между реальным диском и правилами — и второй пограничный слой
`src/tsconfig/` — автопоиск алиасов из `tsconfig.json` (см. ниже).

Обратная совместимость правил и их именования пока не гарантируется; переименование правила не
требует deprecation-цикла.

## Тулинг и команды

Менеджер пакетов — Yarn 4 через corepack (`corepack enable`), Node 20.19+. TypeScript компилируется
через `tsup` в ESM (`dist/`), тесты — `vitest`.

- `yarn verify` — `yarn checks` плюс сборка; ровно это гоняет CI.
- `yarn checks` — линт, `prettier --check`, типы, тесты (без сборки; используется в релизе).
- `yarn test` / `yarn test:watch` — тесты.
- `yarn build` — сборка в `dist/`.
- `yarn smoke [версия-eslint]` — собирает тарбол, ставит его во временный проект и запускает там
  ESLint. Прогоняй после изменений в `package.json` (`exports`, `files`, формат сборки).
- `yarn docs:dev` / `yarn docs:build` / `yarn docs:preview` — сайт документации (см. ниже). В
  `yarn verify` они не входят: сайт собирает отдельный workflow.

Сайт собирается из **всего** `docs/`, и `.github/workflows/docs.yml` выкладывает результат на GitHub
Pages целиком: любой markdown, положенный в `docs/`, становится публичной страницей. Исключений
сейчас нет — `srcExclude` в `docs/.vitepress/config.ts` не задан вовсе. Поэтому рабочий материал, а
не документация (планы, которые `/planning:make` кладёт в `docs/plans/`, черновики идей), в `docs/`
не живёт: либо держи его вне `docs/`, либо заводи `srcExclude` той же правкой, которой кладёшь.

Пакет — ESM-only и рассчитан на flat config ESLint 9.15+ (`peerDependencies`). Нижняя граница —
именно 9.15, потому что документированный способ подключения пресета собран на `extends` из
`defineConfig` (`eslint/config`), а он появился там: пресет действует на все файлы, и удержать его
правила в одной области со схемой слоёв иначе можно только спредом объекта пресета. `require()` из
eslintrc не поддерживается осознанно; менять это — отдельное решение, а не побочный эффект правки
сборки.

Форматирование выполняется автоматически при коммите: хук `.husky/pre-commit` гоняет `lint-staged`
(`prettier --write` и `eslint --fix` по застейдженным файлам) и правит файлы сам. Поэтому не
запускай `prettier`, `eslint --fix` и подобные форматтеры/линтеры вручную — ни `--write`, ни
`--check` «на всякий случай» — и не подгоняй результат руками: переносы строк в markdown под
`printWidth`, отступы, кавычки, запятые расставит хук. Пиши текст и код как удобно, форматирование —
не твоя забота.

## Баррели: границы слоёв внутри `src/`

Репозиторий живёт по тем же правилам, которые проверяет плагин. Каждый слой и модуль внутри `src/`
объявляет публичный интерфейс баррелем `index.ts`: `src/host/`, `src/settings/`, `src/tsconfig/`,
`src/imports/`, `src/path/`, `src/testing/`, `src/rules/`, `src/rules/<имя>/`. Отсюда два правила на
любой импорт:

- **снаружи слоя** — только `@/<слой>/index.js`, никогда напрямую в файл (`@/host/fs.js` из
  `src/rules/` — нарушение `weld/no-barrel-bypass`);
- **внутри слоя** — прямо в соседний файл (`@/settings/aliases.js` из `src/settings/weld.ts`):
  модуль не закрыт от самого себя, и гонять внутренние связи через собственный баррель незачем.

Новый экспорт наружу — это правка барреля, а не просто `export` в файле: список в `index.ts` и есть
осознанно спроектированный интерфейс слоя. Что в баррель не попало, то внутреннее дело слоя.

`src/extensions.ts` и `src/debug.ts` — файлы, а не директории, барреля им не нужно.

## Слой `src/host/` — FS-абстракция

Каркас для всех правил, которым нужен доступ к файловой системе. Правила не трогают диск и
`node:path` напрямую — они работают только с виртуальными posix-путями от корня репозитория
(`/src/feature/x.ts`), которые получают через тип `FsHost` (`hasEntryPoint`, `toVirtual`). Границу
держим узкой: примитив добавляется тогда, когда его просит правило, а не заранее — каждый метод
`FsHost` обязаны реализовать все фейки, и каждый обзаводится своим кэшем. Единственное место,
знающее про реальные пути (буквы дисков, `\`, относительность к `cwd`), — `createFsHost` /
`getFsHost` в `src/host/fs.ts`; для тестов — `createFakeFsHost` из `src/host/fs.testing.ts`,
работающий над списком виртуальных путей без обращения к диску. `src/host/root.ts` отвечает за
автопоиск корня репозитория (`findRepoRoot`). Реальный диск читается только на этой границе; ядро
правил и их тесты её не видят.

Сама арифметика реальных путей — буквы дисков, корень ФС, склейка, подъём вверх, резолв от `cwd`,
общая директория набора путей (`commonRealDirectory` — им `getFsHost` поднимает авто-root до
`coverDirs`) — лежит в `src/host/real-path.ts` и наружу через баррель не выходит: и `fs.ts`, и
`root.ts` задают ей одни и те же вопросы, а пока каждый отвечал у себя, «что считается диском» было
записано тремя разными литералами.

Наружу всё это уходит через `src/host/index.ts` — включая фейки из `fs.testing.ts`: подделка
`FsHost` нужна именно чужим тестам, то есть внешним потребителям слоя, и спрятать её значило бы, что
до неё никто не дотянется. В бандл фейк не попадает — `src/index.ts` его не импортирует, и treeshake
выносит (проверяется `yarn build`).

## Слой `src/settings/` — чтение `settings.weld`

Формат секции `settings.weld` знает только `src/settings/`. Наружу слой отдаёт не сырую секцию, а
геттер на каждую настройку — `getRepoRoot`, `getAliasesBaseUrl`, `getAliases`, `getLayerSchema`
(реализация в `src/settings/weld.ts`, наружу — через `src/settings/index.ts`). Форма у всех одна:
`(settings, overrides?)`, где `overrides` — тип `WeldOverrides`, объект с полем на каждую настройку
секции. Общая форма выбрана вместо позиционных override-ов намеренно: вызывающий передаёт опции
правила целиком и не знает, какая настройка какому геттеру нужна, — иначе каждая новая настройка
меняла бы сигнатуру геттера и все его вызовы. Сам тип объявляет `src/settings/`: набор перекрываемых
настроек это и есть набор полей секции, а знает его только этот слой. По той же причине `overrides`
принимает и `getFsHost(settings, cwd, overrides?, coverDirs?)`.

Значения `overrides` приходят из пользовательского конфига — из одноимённых опций правила (общие
объявляет `WELD_OPTION_PROPERTIES`, схемные — само правило направления, а прокидывает их в геттеры
`resolveWeldContext`, см. «`src/rules/context.ts`»), поэтому проверяются теми же правилами, что и
`settings.weld`, и в сообщении об ошибке называются как `options.<имя>`. Геттер смотрит на своё поле
`overrides` первым и при заданном значении секцию не читает вовсе; у `getAliases` в расчёт идут два
поля сразу — своё и `aliasesBaseUrl`: якоря алиасов отсчитываются от него, и переопределять их
порознь бессмысленно. Правила и `src/host/` не разбирают `settings` сами и не знают ни имён полей,
ни их формата: `src/host/fs.ts` берёт корень через `getRepoRoot` и только резолвит его как реальный
путь. Валидация значений и сообщения об ошибках конфига живут там же, в `src/settings/`.

У разбора алиасов есть кэш с TTL в минуту, общий на оба источника (`getAliases` и
`getAliasesFromPaths`): правило спрашивает алиасы на каждый линтуемый файл, а аргументы приходят те
же по ссылке — в flat config объект `settings` у всех файлов одного конфиг-блока один и тот же, а
`paths` отдаёт по ссылке кэш `src/tsconfig/`. Ключ — тройка аргументов разбора (для `getAliases` это
`settings`, объект `overrides` целиком и `undefined` третьим), поэтому вызывающий обязан передавать
один и тот же объект опций, а не собирать его на каждый файл (см. `EMPTY_OPTIONS` в
«`src/rules/context.ts`»). Кэш устроен списком с линейным поиском, а не `Map`: строкового ключа у
ссылок нет, а собирать его пришлось бы обходом тех же `paths`; записей при этом единицы — по одной
на конфиг-блок. TTL здесь не про свежесть (конфиг в рамках прогона неизменен), а про то, чтобы
записи не жили вечно: перечитанный конфиг языкового сервера иначе навсегда оставлял бы в кэше старый
объект `settings` вместе с разобранными по нему алиасами. Запоминается только успешный разбор — на
сломанном конфиге ESLint должен ругаться на каждом файле, а не на первом. Массив при попадании
возвращается тот же: потребители его только читают.

Кроме геттеров баррель отдаёт два хелпера: `hasAliases(settings, overrides)` — заданы ли алиасы явно
(присутствие ключа; пустой `{}` тоже «задан» и выключает автопоиск tsconfig) — и
`getAliasesFromPaths(paths, virtualBase, source)` — разбор внешних `paths` (формат
`compilerOptions.paths`) теми же правилами, что и `settings.weld.aliases`; `source` называет
источник в тексте ошибки (реальный путь tsconfig). На кривых значениях он бросает так же, как разбор
явных алиасов, — решение «глотать или падать» принадлежит вызывающему. Живёт он рядом с
`getAliases`, в `src/settings/weld.ts`, и делит с ним кэш: решение «алиасы разбираются один раз на
конфиг» должно быть одно на оба источника. Сам `parseAliases` под собственным именем наружу
по-прежнему не выходит.

## `src/settings/layers.ts` — схема слоёв

Вторая настройка со своим разбором (первая — алиасы): `layers`, `moduleLayers` и `moduleDir`
разворачиваются в `LayerSchema` — один плоский упорядоченный список квалифицированных слоёв
(`order`), границы `first`/`last` каждого имени и наборы имён для опознания слоя по пути.
Квалификатор — часть имени: `root:<имя>` (слой проекта), `module:<имя>` (слой модуля), `module`
(модуль как целое), `root:unknown`/`module:unknown` (код без слоя на своём уровне); два уровня живут
в одном списке именно потому, что квалификатор их различает. `@modules` разворачивается в `module`,
слои модуля, снова `module` — модуль как целое получает диапазон вокруг своих слоёв, и весь вердикт
правила сводится к `first(цель) < last(источник)` без единого особого случая. Сырые
`layers`/`moduleLayers`/`moduleDir` наружу не выходят, как и сырые алиасы: арифметика порядка живёт
здесь, потому что она целиком про формат конфига.

Кэша у разбора нет намеренно: он не читает диск, не логирует и не отдаёт наружу ничего, что
сравнивалось бы по ссылке, — проход по десятку строк дешевле поиска в кэше. Кривая схема бросает при
каждом вызове, как и кривые алиасы (ESLint исключение из `create()` не репортит, а пробрасывает: на
сломанном конфиге прогон падает): правило, молча отключившееся на сломанном конфиге, хуже громко
упавшего.

Имена слоёв проверяются на зарезервированные случаи: `@`-имя, отличное от `@modules`/`@unknown`, и
**обычные** `unknown` и `module` — так `plainLayerName` называет спец-слои в сообщениях, и
объявленный слой стал бы от них неотличим (`unknown` вдобавок дал бы тот же квалификатор, что
`@unknown`, и проверка «слой не объявлен» перестала бы срабатывать; `module` дал бы вердикт
`'module' must not import from 'module'`). Имя, которое не может быть сегментом пути, тоже
отвергается — `/`, `.` и `..`: слой — имя директории, иначе он не совпал бы ни с одним сегментом.

`parseLayerSchema` принимает не тройку значений, а тройку `SettingValue` (`{ value, source }`): три
настройки перекрываются порознь (схема — секцией, `moduleDir` — опцией правила), имя места в конфиге
нужно тексту ошибки, а собрать его внутри разбора нельзя — источник знает только геттер
(`pickSetting` в `weld.ts`). Геттеров два: `getLayerSchema` и `hasLayers` — «задана ли схема» по
образцу `hasAliases` (присутствие ключа; `layers: []` тоже «задана» и означает схему без слоёв).

Квалифицированное имя собирается **снаружи** — по пути линтуемого файла, — поэтому баррель отдаёт и
словарь имён: `rootLayer`, `moduleLayer`, `MODULE`, `ROOT_UNKNOWN`, `MODULE_UNKNOWN` и обратную
операцию `plainLayerName` (имя без квалификатора — для сообщений правила: в конфиг пользователь
писал простые имена). Иначе ключи `first`/`last` собирались бы литералами в правиле, и формат
квалификатора знали бы два слоя. Рядом с `plainLayerName` наружу выходит `isModuleLevel`: простое
имя уровень не различает, а `@unknown` бывает на обоих — сообщение, называющее оба конца импорта,
без уровня получилось бы самопротиворечивым («`@unknown` не может импортировать `@unknown`»).
Зарезервировать имя здесь нечего: оба `@unknown` пишет в конфиг сам пользователь, и оба списка
принимают их законно.

## Слой `src/tsconfig/` — автопоиск алиасов из tsconfig

Второй пограничный модуль наряду с `src/host/`: знает формат tsconfig **и** читает диск (через
рантайм-зависимость `get-tsconfig` — поиск ближайшего конфига, JSONC, полный резолв `extends`,
`${configDir}`). Зависимости — `node:path` и `get-tsconfig` (как пограничный слой он вправе трогать
реальные пути), общий словарь `src/debug.ts` и `src/path/`, да пара предикатов формы `*` из
`src/settings/` (см. ниже про `realAnchors`); в `src/host/` и `src/settings/` чтение tsconfig не
лезет намеренно: первый не знает форматов конфигов, второй не читает диск.

Наружу через `src/tsconfig/index.ts` уходит `loadTsconfigPaths(realFilePath)` и тип результата
`TsconfigPaths`: сырые `paths` (валидация — дело `src/settings/`; абсолютные значения после
подстановки `${configDir}` переписаны в относительные от базы), реальные `realBaseDir` (база записей
`paths` по tsconfig-семантике: `baseUrl` конфига, а без него — директория конфига, объявившего
`paths`, через `implicitBaseUrl` из `get-tsconfig`) и `configPath`, плюс `realAnchors` — реальные
якоря записей `paths` для инварианта root (якоря в `node_modules` и записи кривой формы `*`
исключены). Слой отдаёт **реальные** пути: виртуализация возможна только после фиксации root, а root
у вызывающего сам зависит от якорей. Любая проблема tsconfig — `null` и debug
(`eslint-plugin-weld:tsconfig`), не исключение: кривой tsconfig не валит линт. Кэш — мемоизация
«директория файла → результат» с TTL по образцу `TTL_MS` из `src/host/fs.ts` и коротким негативным
TTL по образцу `NEGATIVE_TTL_MS` оттуда же (созданный tsconfig подхватывается за секунды); сброс
(`resetTsconfigCache`) выходит через баррель для чужих тестов, швы `now`/`read` — нет.

## Модули ниже слоёв

`src/path/` (сегментные операции над виртуальными путями; реализация в `posix.ts`, наружу — через
`src/path/index.ts`), `src/extensions.ts` (списки расширений) и `src/debug.ts` (namespace логгеров)
— общий словарь, который импортируют все слои. Они ничего не знают ни про конфиг, ни про диск, ни
про правила, и зависимостей друг на друга не имеют.

В `src/extensions.ts` списка два — `ENTRY_EXTENSIONS` и `MODULE_EXTENSIONS`. Состав у них сегодня
одинаковый, но вопросы разные: первый про то, какой файл делает директорию модулем, второй про то,
что вообще считается импортом кода. Держать их одной константой нельзя: расширение любого из ответов
молча меняло бы второй.

## Слой `src/imports/` — строка импорта ↔ виртуальный путь

Соответствие между специфаером (`'../other/internal.ts'`, `'@/other'`) и виртуальным путём цели
знает только `src/imports/`. Наружу слой отдаёт `parseSpecifier` (специфаер → `Target`: виртуальный
путь, форма записи `Form` и явно записанное расширение) и `renderSpecifier` (обратная сборка
специфаера в той же форме) — реализация в `src/imports/specifier.ts`, наружу через
`src/imports/index.ts`; сами `Target` и `Form` в баррель не выходят: снаружи результат
`parseSpecifier` только передаётся в `renderSpecifier`. Алиасы приходят готовым списком `Alias` из
`src/settings/`, диск слой не трогает — существование цели его не интересует.

Второй модуль слоя — `src/imports/nodes.ts`: где в AST лежит строка-специфаер и как её заменить.
`createSpecifierVisitor(onSpecifier, options?)` отдаёт слушатели для `create()`,
`replaceSpecifier(node, s)` — готовый `Rule.ReportFixer`. Здесь же зафиксированы решения, которые
иначе каждое правило принимало бы заново: репорт вешается на сам литерал пути, а не на весь
оператор; кавычка берётся из исходника; `require` считается импортом — в том числе в
TypeScript-форме `import x = require('...')`, где специфаер лежит не в `source` и не в аргументе
`CallExpression`, а в `TSExternalModuleReference`, и потому требует собственного слушателя
(`TSImportEqualsDeclaration`). Формы этой записи с модификатором (`export import x = require(...)`)
касается то же решение: специфаер в ней один, внешний `ExportNamedDeclaration` своего `source` не
имеет, и при включённых реэкспортах отчёт не удваивается. Список проверяемых форм — часть публичного
поведения обоих правил: добавил форму — правь «Что проверяется» на обеих страницах правил.

Реэкспорт (`export ... from`, `export * from`) — единственная форма, ответ про которую слой не
выбирает за правило: он одновременно и зависимость, и часть публичного интерфейса. Обход включается
опцией `reExports` (по умолчанию выключен), и решение принимает каждое правило само:
`no-barrel-bypass` реэкспорты не обходит (баррель из них и собран — правило репортило бы сам
баррель), `no-illegal-layer-dependency` обходит (для направления зависимостей это обычное ребро
графа, и без него запрет обходился бы переписыванием `import` + `export` в одну строку).

Слой живёт отдельно от правила намеренно: разбор, рендер и обход специфаеров нужны любому правилу
про импорты и ничего не знают ни про баррели, ни про границы модулей. В `src/rules/<имя>/core/`
остаётся только то, что специфично для самого правила (для `no-barrel-bypass` — `barrier.ts`).

## `src/rules/context.ts` — каркас правила

Общие настройки и связка «ESLint-контекст → всё, что правилу нужно до первого узла».
`WELD_OPTION_PROPERTIES` — свойства `meta.schema`, которые правило подмешивает к своим спредом;
`resolveWeldContext<TOwnOptions>(context, fsHost?)` возвращает
`{ fromFile, aliases, fsHost, options }` либо `null`, если линтуемый файл вне корня репозитория.
Параметр — только собственные опции правила: общие известны самому `resolveWeldContext`, и в
`options` он отдаёт их пересечение — `TOwnOptions & WeldOverrides`, то есть общие поля типизованы
как `unknown`: их значения проверяют геттеры `src/settings/`, а не этот каст. Собственного
`WeldOptions` здесь больше нет — набор перекрываемых настроек объявляет `src/settings/`, и вторая
его копия рядом с `resolveWeldContext` разошлась бы с первой. Правило не перечисляет
`repoRoot`/`aliasesBaseUrl`/`aliases` ни в схеме, ни в типе опций и не собирает `FsHost` руками —
иначе четвёртая общая настройка потребовала бы правки каждого правила порознь. Зато опции, общему
набору не принадлежащие (схема слоёв), правило объявляет само — см.
«`src/rules/no-illegal-layer-dependency/`».

Опции берутся из `context.options[0]`, а при их отсутствии подставляется модульная константа
`EMPTY_OPTIONS` — одна и та же ссылка на все файлы: кэш разобранных алиасов ключуется ссылкой на
объект опций, и `?? {}` промахивался бы мимо него всегда.

Приоритет источников алиасов: `options.aliases` → `settings.weld.aliases` → автопоиск tsconfig. Явно
заданные алиасы (по `hasAliases`, пустой `{}` тоже «задан») или инъекция `fsHostOverride` выключают
автопоиск — тогда всё работает как раньше. Иначе `resolveWeldContext` зовёт
`loadTsconfigPaths(context.filename)` и держит инвариант «root покрывает якоря алиасов»: найденные
`realAnchors` безусловно уходят в `coverDirs` для `getFsHost`, и при автоопределении root
поднимается до общей директории `findRepoRoot(cwd) ?? cwd` и якорей (поэтому в монорепе разные
линтуемые файлы могут получить разный root и разные инстансы `FsHost` — ожидаемо). Что явный root
якоря игнорирует, решает сам `getFsHost` — здесь это не переспрашивается; зато tsconfig вне явного
root (`toVirtual(configPath) === null`) отбрасывается целиком. Дальше — `getAliasesFromPaths` в
`try/catch`: исключение или база вне root → debug (`eslint-plugin-weld:rules`) и пустые алиасы,
кривой tsconfig линт не валит (в отличие от явных алиасов, где падение намеренное).
`settings.weld.aliasesBaseUrl` на tsconfig-алиасы не влияет — их база приходит из самого tsconfig.

Модуль лежит выше `src/host/` и `src/settings/`: решение «опции правила перекрывают `settings.weld`»
не принадлежит ни тому, ни другому. Полной изоляции слоёв друг от друга при этом нет: `src/host/`
берёт корень репозитория через `getRepoRoot` — осознанная односторонняя зависимость
`host → settings`. Значение лежит в конфиге, формат которого знает только `src/settings/`, а
резолвить его как реальный путь может только `src/host/` — поэтому `host` спрашивает значение у
геттера, по-прежнему не зная ни имён полей, ни формата секции.

Второй параметр `fsHost` — шов для тестов, общий на все правила. Шов именно параметром, а не
модульным мутабельным состоянием: иначе тесты зависели бы от порядка запуска.

## `src/rules/no-illegal-layer-dependency/` — направление зависимостей

Второе правило и первое со своими опциями. Три настройки схемы (`layers`, `moduleLayers`,
`moduleDir`) оно объявляет в своей `meta.schema` само (`SCHEMA_OPTION_PROPERTIES` плюс спред
`WELD_OPTION_PROPERTIES`), а не добавляет к общим: соседнее правило схему не читает, и принимать
`layers` в его опциях значило бы принимать и молча игнорировать. По той же причине схема не идёт в
`WeldContext`: кривой `settings.weld.layers` уронил бы `no-barrel-bypass`, которому она не нужна.
Схема при этом обязательна — включённое без `layers` правило бросает `MISSING_SCHEMA` из `create()`,
то есть роняет прогон ESLint на первом же файле под правилом: молча отключившееся правило хуже
громко упавшего.

Диск правило не читает вовсе: слой опознаётся по именам сегментов виртуального пути, существование
цели импорта на вердикт не влияет, и `FsHost` здесь нужен только чтобы виртуализовать путь
линтуемого файла.

В `core/` — две чистые функции, обе покрыты таблицами ожиданий:

- `layer-of.ts`: путь → `{ layer, owner, moduleRoot }`. Слой — самое глубокое совпадение в своём
  контексте (вне модулей сегменты сверяются с `projectLayers`, внутри модуля — с `moduleLayers`), а
  вход в модуль сбрасывает найденный снаружи слой: у модуля своя система слоёв. У линтуемого файла
  сканируется только `dirname` (имя файла слоя не заявляет), у цели импорта — весь записанный путь:
  `@/modules/order` это баррель модуля, и разворачивать его в `…/order/index.ts` нельзя — иначе
  самый канонический легальный импорт репортился бы как нарушение. `owner` — директория найденного
  слоя (у модуля как целого и его неразмеченного кода — директория модуля): совпавшие владельцы
  делают импорт внутренним, и правило молчит; `moduleRoot` отличает свой модуль от чужого;
- `verdict.ts`: `decide(schema, from, to)` — сравнение двух позиций плюс классификация нарушения по
  пяти из шести сообщений. Здесь же `sourceRights` (неразмеченный код модуля живёт по правам модуля
  целиком) и `declareHint` (совет «как объявить слой»): оба нужны и вердикту, и самому правилу —
  шестое сообщение, репорт на файл со слоем вне схемы, живёт вне `decide`. Совет в каждом сообщении
  обязан быть конфигом, который разбор схемы примет: поэтому цель внутри модуля при схеме без
  `@modules` уходит в `undeclaredTargetLayer` («объяви `@modules`»), а не в `moduleInternals`, чей
  совет про `moduleLayers` без `@modules` — ошибка конфига; по той же причине `horizontalDependency`
  называет список, в котором объявляется смежный повтор (`moduleLayers` для слоя модуля: тот же
  повтор в `layers` разбор схемы отверг бы). Имена в сообщениях — простые, но одно простое имя может
  прийти с двух уровней (`@unknown` объявляется в обоих списках), поэтому у такой пары своё
  сообщение — `illegalDependencyAcrossLevels` с уровнем каждого конца; на одном уровне совпадение
  имён означало бы один и тот же слой, то есть горизонталь.

`pipeline.ts` — склейка `parseSpecifier` → `layerOf` → `decide`, собираемая на файл. Отдаёт не голую
функцию (как у соседа), а `{ fromRights, checkImport }`: слой линтуемого файла нужен ещё и репорту
на `Program`, а считать его там второй раз значило бы опознавать один путь дважды — и схлопывать
`sourceRights` во втором месте. Наружу выходит именно схлопнутое имя, а не всё положение файла:
владелец и модуль нужны только вердикту, и правило их не видит.

## `src/testing/` — общий каркас тестов

`rule-tester.ts` (`createRuleTester` — парсер и уровень языка в одном месте), `paths.ts`
(`repoRoot`, `fixtureRoot`, `consumerFile`) и сама фикстура `fixtures/project/` — минимальный проект
с барьером. Ничего специфичного для конкретного правила здесь нет, поэтому каркас не живёт внутри
одного из них: иначе тесты второго правила тянули бы его через сосед-правило либо завели бы копию, и
настройки парсера разъехались бы.

`paths.ts` отдаёт готовые константы, а не хелпер вида `dirFromUrl(url)`: тот считает путь от
`import.meta.url` своего модуля, поэтому один и тот же вызов из разных файлов означал бы разное.

Фейки живут рядом с тем, что подделывают (`src/host/fs.testing.ts`), а не здесь: `src/testing/` —
про инфраструктуру запуска тестов, `*.testing.ts` — про конкретный слой.

Вторая группа фикстур — `fixtures/tsconfig/*`: мини-проекты для автопоиска tsconfig (basic,
monorepo, extends-package, jsonc, broken, no-paths), по константе на сценарий в `paths.ts`
(`tsconfigFixturesRoot` и `tsconfig*Fixture`).

Сценарии, которые фикстурой не выражаются (правка файла между вызовами, директория без `.git` над
ней), собирает `tmp-project.ts`: `makeTmpProject(files)` создаёт временный проект из пар
«относительный путь → содержимое», `cleanupTmpProjects()` убирает всё созданное и зовётся из
`afterEach` теста. Уборка не на вызывающем намеренно: `try/finally` вокруг каждого сценария
расползается по тестам и теряет директорию на упавшем assert.

Наружу модуль отдаёт `createRuleTester`, `repoRoot`, `fixtureRoot`, `consumerFile`, `consumerJsFile`
(тот же потребитель для конфигов без TS-парсера), константы tsconfig-фикстур и
`makeTmpProject`/`cleanupTmpProjects` — через `src/testing/index.ts`. Сами фикстуры через баррель не
проходят и не могут: тесты обращаются к ним как к путям на диске, а не как к модулям.

Инфраструктурные соглашения по фикстурам: поддельная `node_modules` внутри фикстур коммитится через
исключение `!src/testing/fixtures/**/node_modules/` в `.gitignore`, а вся
`src/testing/fixtures/tsconfig/` выведена из-под prettier строкой в `.prettierignore` (фикстуры —
данные, их формат — часть сценария). Новая фикстура вне этих путей молча сломает `yarn checks` —
добавляй её рядом либо расширь исключения.

## Добавление правила

1. Реализовать правило в директории `src/rules/<имя>/` (например, `index.ts` с самим правилом,
   `core/`, `pipeline.ts` — по необходимости) и зарегистрировать в `src/rules/index.ts`. Настройки и
   `FsHost` правило берёт через `resolveWeldContext` (см. выше), диск не читает; обход импортов —
   через `createSpecifierVisitor`. Чужие слои импортируются только через их баррели (см. «Баррели»).
   Своим остаётся только то, что специфично для правила.
2. Тесты — рядом с тестируемым кодом внутри той же директории (`src/rules/<имя>/*.test.ts`), поверх
   `createRuleTester` и фикстуры из `src/testing/`; инвариант «у правила есть `meta.docs` и
   `meta.messages`» проверяется автоматически. Про язык `meta.messages` — см. «Язык».
3. Завести страницу правила `docs/rules/<имя>.md` со ссылкой наверх — на идею подхода, которую
   правило проверяет, — и добавить её в навигацию `docs/.vitepress/config.ts` (сама она туда не
   попадёт).
4. Связать правило с документацией подхода: идея, которую правило проверяет, должна быть описана
   статьёй в `docs/core-concepts/` (тезисы тех же идей — в `docs/index.md`,
   `docs/get-started/overview.md` и `README.md`; правка идеи — правка всех трёх, см. «Текущее
   состояние»). Правило без парного раздела считается расхождением двух частей репозитория; если для
   идеи раздела ещё нет — сначала раздел. Заодно правится список правил и абзац о статусе в
   `README.md`.
5. Решить, входит ли правило в `configs.recommended` (`src/index.ts`).

## Релиз

Релиз (`.github/workflows/release.yml`) запускается двумя способами:

- **Вручную** через `workflow_dispatch`: выбираешь тип бампа — ключевые слова `npm version` как есть
  (`patch` / `minor` / `major` / `prepatch` / `preminor` / `premajor` / `prerelease`) — и
  идентификатор пререлиза (`rc` / `beta` / `alpha`). Базой служит максимальный по semver тег
  репозитория — именно максимальный, а не ближайший в истории ветки: после amend/rebase теги
  остаются на осиротевших коммитах, и бамп от видимого из ветки тега упирается в уже занятую в npm
  версию. Отсюда `fetch-depth: 0` в checkout; всю semver-арифметику делает `npm version`. Тег
  создаётся вместе с GitHub Release уже после успешной публикации, поэтому неудачный прогон не
  оставляет тег в репозитории.
- **Git-тегом `vX.Y.Z`** — тогда источник версии просто имя тега.

В `package.json` лежит заглушка `0.0.0`, версию проставляет workflow перед упаковкой. `plugin.meta`
(`name`, `version`) читается из `package.json` в рантайме, поэтому отдельно синхронизировать её в
коде не нужно. Бампить версию в `package.json` коммитом не нужно ни при одном из способов.

Версии с пререлизным суффиксом уезжают под dist-tag `next` и помечаются prerelease в GitHub Release;
обычные — под `latest`.

Итоги прогона workflow пишет в GitHub Job Summary: версию, dist-tag, базу и тип бампа (или тег
пуша), базу заметок и коммит — плюс ссылки на npm и GitHub Release после публикации. Таблица
появляется сразу после расчёта версии, поэтому видна и когда публикация упала.

Автоматические заметки к GitHub Release считаются от максимального **стабильного** тега `vX.Y.Z`
репозитория (`--notes-start-tag`), а не от предыдущего тега вообще: иначе после серии `rc` в
заметках финального релиза окажутся только изменения с последнего `rc`, а не весь релизный цикл.
Стартовый тег ищется по списку тегов, а не через `git describe`: тот видит только достижимые от HEAD
теги, а после amend/rebase они остаются на осиротевших коммитах — та же причина, что и у базы
версии. Если стартовый тег не передать, `gh --generate-notes` молча возьмёт предыдущий релиз, то
есть соседний `rc`.

Публикация двухшаговая. Workflow доводит дело до `npm stage publish`: версия уезжает в реестр
закрытой, установить её нельзя. Публикует человек, локально и с 2FA:

```sh
npm stage list eslint-plugin-weld   # найти stage-id нужной версии
npm stage view <stage-id>           # посмотреть, что именно уедет
npm stage approve <stage-id>        # собственно публикация
npm stage reject <stage-id>         # отменить ненужный стейдж
```

Обычный `npm publish` вручную не запускай — он обходит этот порядок и публикует без provenance.

## Язык

Документация и коммиты — на русском (см. `README.md` и историю git). Придерживайся этого для новых
документов и сообщений коммитов; идентификаторы в коде и имена ESLint-правил — на английском.

**Всё, что плагин выводит в рантайме, — на английском.** Это сообщения правил (`meta.messages`),
тексты `throw new Error` при невалидном конфиге и строки `debug(...)`. Пользователь плагина
по-русски не читает, а сообщения об ошибках попадают в вывод ESLint и в баг-репорты. Русский
остаётся в коде только в комментариях, JSDoc и заголовках тестов.
