# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this
repository.

## Что это за репозиторий

WELD (Well-Encapsulated Layered Design) — подход к организации кода во frontend-приложениях плюс
инструменты для автоматической проверки его правил. Репозиторий должен содержать две связанные
части:

1. **Документацию подхода** — как раскладывать приложение по слоям и где проводить границы между
   модулями.
2. **ESLint-плагин** — проверку этих правил в CI/редакторе, потому что договорённостями в команде
   такие границы не удерживаются.

Ключевые идеи, задающие рамку для любых решений здесь:

- **Строгая инкапсуляция.** Модуль публикует наружу узкий, осознанно спроектированный интерфейс; всё
  остальное — его внутреннее дело.
- **Слои задают направление зависимостей**, инкапсуляция не даёт зависимостям расползтись в обход
  этого направления.

Правило плагина без соответствующего раздела в документации (и наоборот) — признак того, что две
части разошлись.

## Текущее состояние

Каркас пакета `eslint-plugin-weld` готов (сборка, тесты, CI, автопубликация); реализовано первое
правило — `weld/no-barrel-bypass` (`src/rules/no-barrel-bypass/`), зарегистрировано в
`src/rules/index.ts` и включено в `configs.recommended`/`configs.strict`. Документация подхода как
таковая ещё не написана — есть только страница правила, `docs/rules/no-barrel-bypass.md` (см.
«Добавление правила» ниже).

Есть слой `src/host/` — граница между реальным диском и правилами (см. ниже).

Обратная совместимость правил и их именования пока не гарантируется; переименование правила не
требует deprecation-цикла.

## Тулинг и команды

Менеджер пакетов — Yarn 4 через corepack (`corepack enable`), Node 20.19+. TypeScript компилируется
через `tsup` в ESM (`dist/`), тесты — `vitest`.

- `yarn verify` — `yarn checks` плюс сборка; ровно это гоняет CI.
- `yarn checks` — линт, `prettier --check`, типы, тесты (без сборки; используется в релизе).
- `yarn test` / `yarn test:watch` — тесты.
- `yarn build` — сборка в `dist/`.
- `yarn smoke [версия-eslint]` — собирает тарбол, ставит его во временный проект и запускает там
  ESLint. Прогоняй после изменений в `package.json` (`exports`, `files`, формат сборки).

Пакет — ESM-only и рассчитан на flat config ESLint 9+. `require()` из eslintrc не поддерживается
осознанно; менять это — отдельное решение, а не побочный эффект правки сборки.

Перед коммитом хук `.husky/pre-commit` сам гоняет `lint-staged` (`prettier --write` и `eslint --fix`
по застейдженным файлам) и правит файлы автоматически. Не запускай `prettier`, `eslint --fix` и
подобные форматтеры/линтеры вручную перед коммитом — это сделает pre-commit хук.

## Баррели: границы слоёв внутри `src/`

Репозиторий живёт по тем же правилам, которые проверяет плагин. Каждый слой и модуль внутри `src/`
объявляет публичный интерфейс баррелем `index.ts`: `src/host/`, `src/settings/`, `src/imports/`,
`src/path/`, `src/testing/`, `src/rules/`, `src/rules/<имя>/`. Отсюда два правила на любой импорт:

- **снаружи слоя** — только `@/<слой>/index.js`, никогда напрямую в файл (`@/host/fs.js` из
  `src/rules/` — нарушение `weld/no-barrel-bypass`);
- **внутри слоя** — прямо в соседний файл (`@/settings/aliases.js` из `src/settings/weld.ts`):
  модуль не закрыт от самого себя, и гонять внутренние связи через собственный баррель незачем.

Новый экспорт наружу — это правка барреля, а не просто `export` в файле: список в `index.ts` и есть
осознанно спроектированный интерфейс слоя. Что в баррель не попало, то внутреннее дело слоя.

`src/extensions.ts` и `src/debug.ts` — файлы, а не директории, барреля им не нужно.

## Слой `src/host/` — FS-абстракция

Каркас для всех правил, которым нужен доступ к файловой системе. Правила не трогают диск и
`node:path` напрямую — они работают только с виртуальными posix-путями от корня репозитория
(`/src/feature/x.ts`), которые получают через тип `FsHost` (`hasEntryPoint`, `toVirtual`). Границу
держим узкой: примитив добавляется тогда, когда его просит правило, а не заранее — каждый метод
`FsHost` обязаны реализовать все фейки, и каждый обзаводится своим кэшем. Единственное место,
знающее про реальные пути (буквы дисков, `\`, относительность к `cwd`), — `createFsHost` /
`getFsHost` в `src/host/fs.ts`; для тестов — `createFakeFsHost` из `src/host/fs.testing.ts`,
работающий над списком виртуальных путей без обращения к диску. `src/host/root.ts` отвечает за
автопоиск корня репозитория (`findRepoRoot`). Реальный диск читается только на этой границе; ядро
правил и их тесты её не видят.

Сама арифметика реальных путей — буквы дисков, корень ФС, склейка, подъём вверх, резолв от `cwd` —
лежит в `src/host/real-path.ts` и наружу через баррель не выходит: и `fs.ts`, и `root.ts` задают ей
одни и те же вопросы, а пока каждый отвечал у себя, «что считается диском» было записано тремя
разными литералами.

Наружу всё это уходит через `src/host/index.ts` — включая фейки из `fs.testing.ts`: подделка
`FsHost` нужна именно чужим тестам, то есть внешним потребителям слоя, и спрятать её значило бы, что
до неё никто не дотянется. В бандл фейк не попадает — `src/index.ts` его не импортирует, и treeshake
выносит (проверяется `yarn build`).

## Слой `src/settings/` — чтение `settings.weld`

Формат секции `settings.weld` знает только `src/settings/`. Наружу слой отдаёт не сырую секцию, а
геттер на каждую настройку — `getRepoRoot`, `getAliasesBaseUrl`, `getAliases` (реализация в
`src/settings/weld.ts`, наружу — через `src/settings/index.ts`); каждый принимает `settings` и
необязательный `override` — значение этой настройки, подставляемое вместо конфига. `override`
приходит из пользовательского конфига — из одноимённых опций правила (их объявляет
`WELD_OPTION_PROPERTIES`, а прокидывает в геттеры и в `getFsHost` — `resolveWeldContext`, см.
«`src/rules/context.ts`»), поэтому проверяется теми же правилами, что и `settings.weld`, и в
сообщении об ошибке называется как `options.<имя>`. У `getAliases` override-ов два — свой и
`aliasesBaseUrl`: якоря алиасов отсчитываются от него, и переопределять их порознь бессмысленно.
Правила и `src/host/` не разбирают `settings` сами и не знают ни имён полей, ни их формата:
`src/host/fs.ts` берёт корень через `getRepoRoot` и только резолвит его как реальный путь. Валидация
значений и сообщения об ошибках конфига живут там же, в `src/settings/`.

## Модули ниже слоёв

`src/path/` (сегментные операции над виртуальными путями; реализация в `posix.ts`, наружу — через
`src/path/index.ts`), `src/extensions.ts` (списки расширений) и `src/debug.ts` (namespace логгеров)
— общий словарь, который импортируют все слои. Они ничего не знают ни про конфиг, ни про диск, ни
про правила, и зависимостей друг на друга не имеют.

В `src/extensions.ts` списка два — `ENTRY_EXTENSIONS` и `MODULE_EXTENSIONS`. Состав у них сегодня
одинаковый, но вопросы разные: первый про то, какой файл делает директорию модулем, второй про то,
что вообще считается импортом кода. Держать их одной константой нельзя: расширение любого из ответов
молча меняло бы второй.

## Слой `src/imports/` — строка импорта ↔ виртуальный путь

Соответствие между специфаером (`'../other/internal.ts'`, `'@/other'`) и виртуальным путём цели
знает только `src/imports/`. Наружу слой отдаёт `parseSpecifier` (специфаер → `Target`: виртуальный
путь, форма записи `Form` и явно записанное расширение) и `renderSpecifier` (обратная сборка
специфаера в той же форме) — реализация в `src/imports/specifier.ts`, наружу через
`src/imports/index.ts`; сами `Target` и `Form` в баррель не выходят: снаружи результат
`parseSpecifier` только передаётся в `renderSpecifier`. Алиасы приходят готовым списком `Alias` из
`src/settings/`, диск слой не трогает — существование цели его не интересует.

Второй модуль слоя — `src/imports/nodes.ts`: где в AST лежит строка-специфаер и как её заменить.
`createSpecifierVisitor(onSpecifier)` отдаёт слушатели для `create()`, `replaceSpecifier(node, s)` —
готовый `Rule.ReportFixer`. Здесь же зафиксированы решения, которые иначе каждое правило принимало
бы заново: репорт вешается на сам литерал пути, а не на весь оператор; кавычка берётся из исходника;
`require` считается импортом, а `export ... from` — нет.

Слой живёт отдельно от правила намеренно: разбор, рендер и обход специфаеров нужны любому правилу
про импорты и ничего не знают ни про баррели, ни про границы модулей. В `src/rules/<имя>/core/`
остаётся только то, что специфично для самого правила (для `no-barrel-bypass` — `barrier.ts`).

## `src/rules/context.ts` — каркас правила

Общие настройки и связка «ESLint-контекст → всё, что правилу нужно до первого узла».
`WELD_OPTION_PROPERTIES` — свойства `meta.schema`, которые правило подмешивает к своим спредом;
`resolveWeldContext<TOptions>(context, fsHost?)` возвращает `{ fromFile, aliases, fsHost, options }`
(`options` — уже разобранные опции правила, включая его собственные) либо `null`, если линтуемый
файл вне корня репозитория. Правило не перечисляет `repoRoot`/`aliasesBaseUrl`/`aliases` у себя и не
собирает `FsHost` руками — иначе четвёртая общая настройка потребовала бы правки каждого правила
порознь.

Модуль лежит выше `src/host/` и `src/settings/`: решение «опции правила перекрывают `settings.weld`»
не принадлежит ни тому, ни другому. Полной изоляции слоёв друг от друга при этом нет: `src/host/`
берёт корень репозитория через `getRepoRoot` — осознанная односторонняя зависимость
`host → settings`. Значение лежит в конфиге, формат которого знает только `src/settings/`, а
резолвить его как реальный путь может только `src/host/` — поэтому `host` спрашивает значение у
геттера, по-прежнему не зная ни имён полей, ни формата секции.

Второй параметр `fsHost` — шов для тестов, общий на все правила. Шов именно параметром, а не
модульным мутабельным состоянием: иначе тесты зависели бы от порядка запуска.

## `src/testing/` — общий каркас тестов

`rule-tester.ts` (`createRuleTester` — парсер и уровень языка в одном месте), `paths.ts`
(`repoRoot`, `fixtureRoot`, `consumerFile`) и сама фикстура `fixtures/project/` — минимальный проект
с барьером. Ничего специфичного для конкретного правила здесь нет, поэтому каркас не живёт внутри
одного из них: иначе тесты второго правила тянули бы его через сосед-правило либо завели бы копию, и
настройки парсера разъехались бы.

`paths.ts` отдаёт готовые константы, а не хелпер вида `dirFromUrl(url)`: тот считает путь от
`import.meta.url` своего модуля, поэтому один и тот же вызов из разных файлов означал бы разное.

Фейки живут рядом с тем, что подделывают (`src/host/fs.testing.ts`), а не здесь: `src/testing/` —
про инфраструктуру запуска тестов, `*.testing.ts` — про конкретный слой.

Наружу модуль отдаёт `createRuleTester`, `repoRoot`, `fixtureRoot`, `consumerFile` и
`consumerJsFile` (тот же потребитель для конфигов без TS-парсера) через `src/testing/index.ts`.
Фикстура `fixtures/project/` через баррель не проходит и не может: тесты обращаются к ней как к
путям на диске, а не как к модулям.

## Добавление правила

1. Реализовать правило в директории `src/rules/<имя>/` (например, `index.ts` с самим правилом,
   `core/`, `pipeline.ts` — по необходимости) и зарегистрировать в `src/rules/index.ts`. Настройки и
   `FsHost` правило берёт через `resolveWeldContext` (см. выше), диск не читает; обход импортов —
   через `createSpecifierVisitor`. Чужие слои импортируются только через их баррели (см. «Баррели»).
   Своим остаётся только то, что специфично для правила.
2. Тесты — рядом с тестируемым кодом внутри той же директории (`src/rules/<имя>/*.test.ts`), поверх
   `createRuleTester` и фикстуры из `src/testing/`; инвариант «у правила есть `meta.docs` и
   `meta.messages`» проверяется автоматически. Про язык `meta.messages` — см. «Язык».
3. Описать правило в документации подхода — правило без парного раздела в документации считается
   расхождением двух частей репозитория. До того как документация подхода WELD появится, парным
   разделом для правила считается его страница в `docs/rules/<имя>.md`.
4. Решить, входит ли правило в `configs.recommended` (`src/index.ts`).

## Релиз

Релиз (`.github/workflows/release.yml`) запускается двумя способами:

- **Вручную** через `workflow_dispatch`: выбираешь тип бампа — ключевые слова `npm version` как есть
  (`patch` / `minor` / `major` / `prepatch` / `preminor` / `premajor` / `prerelease`) — и
  идентификатор пререлиза (`rc` / `beta` / `alpha`). Базой служит максимальный по semver тег
  репозитория — именно максимальный, а не ближайший в истории ветки: после amend/rebase теги
  остаются на осиротевших коммитах, и бамп от видимого из ветки тега упирается в уже занятую в npm
  версию. Отсюда `fetch-depth: 0` в checkout; всю semver-арифметику делает `npm version`. Тег
  создаётся вместе с GitHub Release уже после успешной публикации, поэтому неудачный прогон не
  оставляет тег в репозитории.
- **Git-тегом `vX.Y.Z`** — тогда источник версии просто имя тега.

В `package.json` лежит заглушка `0.0.0`, версию проставляет workflow перед упаковкой. `plugin.meta`
(`name`, `version`) читается из `package.json` в рантайме, поэтому отдельно синхронизировать её в
коде не нужно. Бампить версию в `package.json` коммитом не нужно ни при одном из способов.

Версии с пререлизным суффиксом уезжают под dist-tag `next` и помечаются prerelease в GitHub Release;
обычные — под `latest`.

Итоги прогона workflow пишет в GitHub Job Summary: версию, dist-tag, базу и тип бампа (или тег
пуша), базу заметок и коммит — плюс ссылки на npm и GitHub Release после публикации. Таблица
появляется сразу после расчёта версии, поэтому видна и когда публикация упала.

Автоматические заметки к GitHub Release считаются от максимального **стабильного** тега `vX.Y.Z`
репозитория (`--notes-start-tag`), а не от предыдущего тега вообще: иначе после серии `rc` в
заметках финального релиза окажутся только изменения с последнего `rc`, а не весь релизный цикл.
Стартовый тег ищется по списку тегов, а не через `git describe`: тот видит только достижимые от HEAD
теги, а после amend/rebase они остаются на осиротевших коммитах — та же причина, что и у базы
версии. Если стартовый тег не передать, `gh --generate-notes` молча возьмёт предыдущий релиз, то
есть соседний `rc`.

Публикация двухшаговая. Workflow доводит дело до `npm stage publish`: версия уезжает в реестр
закрытой, установить её нельзя. Публикует человек, локально и с 2FA:

```sh
npm stage list eslint-plugin-weld   # найти stage-id нужной версии
npm stage view <stage-id>           # посмотреть, что именно уедет
npm stage approve <stage-id>        # собственно публикация
npm stage reject <stage-id>         # отменить ненужный стейдж
```

Обычный `npm publish` вручную не запускай — он обходит этот порядок и публикует без provenance.

## Язык

Документация и коммиты — на русском (см. `README.md` и историю git). Придерживайся этого для новых
документов и сообщений коммитов; идентификаторы в коде и имена ESLint-правил — на английском.

**Всё, что плагин выводит в рантайме, — на английском.** Это сообщения правил (`meta.messages`),
тексты `throw new Error` при невалидном конфиге и строки `debug(...)`. Пользователь плагина
по-русски не читает, а сообщения об ошибках попадают в вывод ESLint и в баг-репорты. Русский
остаётся в коде только в комментариях, JSDoc и заголовках тестов.
